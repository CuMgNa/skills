# 中文两层文档审核规范

本文件是 `doc-reviewer` 的详细审核标准。`SKILL.md` 负责流程编排，本文件负责事实台账、角色边界、问题分类、误报控制、去重、脱敏和最终报告结构。

## 一、事实台账

审核角色启动前，先建立内部事实台账。

每条事实建议包含：

```text
事实编号：F-001
位置：标题路径 + 行号/段落/页码/工作表与单元格
最小证据：证明事实所需的最短原文
归一化含义：不改变原意的简要概括
实体：对象、模块、缺陷、模板或指标
时间：统计时间、发生时间或版本时间
版本/环境：版本、终端、部署环境
范围：全量、局部、部分执行、未覆盖等
单位与分母：条、个、百分比及计算口径
来源类型：待审文档 / 用户指定真源
确定性：明确 / 内部矛盾 / 口径不明 / 需外部核验
敏感标记：无 / 需脱敏
```

### 1.1 真源规则

只有用户明确指定某项资料为权威真源，或在审核前明确确认它是当前生效依据时，才能作为跨源核验依据。资料具备正式版本、时间和来源，只能说明它可能适合作为候选依据，不能由审核者自行升级为真源。

以下内容不自动视为真源：

- 待审文档自身未提供的引用资料；
- 文件名相似的历史报告；
- 团队惯例或审核者经验；
- 常见模板；
- 合理但没有证据的业务或技术推断。

无真源时只能判定“文档内部是否一致”，不能写成“真实数据错误”。

## 二、第一层：专业测试负责人

专业测试负责人建立专业基线，不与第二层争夺表达权。

### 2.1 数据与统计

检查：

- 总数与分项之和；
- 百分比、分母和舍入方式；
- 正文、表格、图示与结论中的重复数字；
- 缺陷总数、各等级数量和清单明细；
- 同一对象的快照值与累计值；
- 同一指标在不同时间、环境、版本和范围下的差异；
- 状态是否互斥，分类是否允许重叠；
- “未执行”是否被错误当作“通过”或“无问题”。

当分类可能重叠、时间不同或分母不明时，不能直接相加后替作者选择正确数字。

### 2.2 测试逻辑和专业性

检查：

- 文档目的和需要支持的决定是否清楚；
- 测试范围、排除项、部分执行和未覆盖是否可识别；
- 执行状态是否支持质量结论；
- 缺陷状态、剩余风险和上线/验收建议是否一致；
- 证据是否足以支持“全部通过”“无风险”“可以上线”等绝对结论；
- 是否区分执行完成、测试通过、质量接受、缺陷修复、回归通过、工单关闭和允许上线；
- 风险、负责人、下一步和完成条件是否形成闭环；
- 专业术语、指标和缺陷等级是否在同一文档中保持一致。

### 2.3 语言质量

检查：

- 错别字和标点；
- 病句和语义残缺；
- 指代对象不清；
- 缩写、内部简称和专业术语未解释；
- 同一实体使用多个名称；
- “全部、基本、正常、处理完、灵活处理、暂无”等模糊或绝对表达；
- 悬空引用、引用章节或附件不存在；
- 建议动作缺少责任、条件或时间点。

### 2.4 专业基线内部结构

```text
文档意图：
当前状态：
主结论：
关键证据：
主要风险：
责任与下一步：
已确认问题：
表达风险：
待确认事实：
覆盖限制：
```

专业基线仅供后续比较，不作为一篇独立报告输出。

## 三、第二层：岗位契约

每个岗位独立阅读原文，在看不到专业基线和其他岗位意见的情况下先复述理解。

共同回答：

1. 文档要解决什么问题？
2. 当前处于什么状态？
3. 主要结论是什么？
4. 最关键的依据是什么？
5. 主要风险或影响是什么？
6. 谁应当在什么条件下采取什么行动？
7. 文档要求本岗位作出什么决定？

### 3.1 项目经理

重点检查：

- 范围、里程碑、依赖和进度是否可追踪；
- 当前状态是否足以支持交付或上线排期；
- 谁负责、何时完成、什么条件下重新决策；
- 未覆盖、阻塞、延期和风险接受是否有明确处理方式；
- 文档是否可能让项目侧误以为测试已经放行。

不得自行决定测试范围、缺陷等级或上线策略。

### 3.2 研发负责人

重点检查：

- 技术问题或根因是否有文档证据；
- 修复完成、部署完成、回归通过和工单关闭是否被混淆；
- 技术责任、系统依赖、接口/数据影响是否明确；
- 修复、验证、上线、回滚和监控动作是否可执行；
- 测试结论是否足以指导研发确认、修复或配合回归；
- 同一根因是否影响多个独立载体、通道或缺陷记录。

不得臆造代码状态、架构根因、修复方案或部署结果。

### 3.3 产品经理或业务负责人

重点检查：

- 测试问题对用户、业务、运营或验收的意义；
- 测试指标是否被错误等同于业务风险低；
- 未覆盖场景和剩余风险是否能支持业务决策；
- 产品或业务需要接受、延期、限制还是阻止什么；
- 专业测试语言是否解释了实际用户影响。

不得凭空补充影响用户数、金额、概率或业务结论。

### 3.4 跨岗位可读性视角

仅在需要时启用，检查：

- 不具备测试背景的人能否理解当前状态、风险和下一步；
- 缩写、模板字段、状态标签和内部术语是否解释；
- 长句、并列条件和隐含前提是否造成歧义；
- 读者是否可能只看结论就得到与正文相反的判断。

它是横向理解检查，不是组织岗位，也不负责判定专业事实。

### 3.5 岗位内部返回结构

```text
岗位：
独立复述：
- 文档目的：
- 当前状态：
- 主结论：
- 关键依据：
- 主要风险：
- 责任与下一步：
- 需要作出的决定：
理解困难：
- 位置：
- 原文：
- 实际理解：
- 另一种合理理解：
- 可能造成的错误行动：
```

第二层不返回完整专业问题卡，不直接推翻专业数据判断。

## 四、问题分类与级别

### 4.1 性质

#### 已确认问题

文档内部已有充分证据证明问题，例如：

- 明确错别字或病句；
- 同一对象在相同时间、版本、环境和范围下使用互斥数字或状态；
- 总数和互斥分项不能闭合；
- 结论与明确记录的失败、阻塞或剩余风险冲突；
- 同一术语指向同一对象却前后命名不一致；
- 引用的章节、附件、责任人或动作在文档中不存在。

#### 表达与理解风险

文字可能有一种正确意图，但合理读者会形成不同理解，例如：

- 专业术语、缩写或状态未解释；
- 范围、时间、分母或主语不清；
- “已解决”没有区分修复、验证和关单；
- 岗位能够从文字推导出不同的下一步；
- 关键上下文只靠团队隐含知识。

#### 待作者确认

正确改法取决于无法从文档恢复的作者意图，例如：

- 分类可能重叠，无法判断应改总数还是分项；
- 两个状态可能对应不同时间或生命周期；
- 风险可能已接受、延期或仍未处理；
- 真实强制范围和条件性范围不明确；
- 发布建议依赖未提供的项目规则。

#### 覆盖限制

不是文档缺陷，而是审核无法覆盖的区域，例如：

- 页面、表格、附件或图片无法读取；
- 文档引用的真源未提供；
- 内容被截断；
- 文件格式无法可靠提取。

### 4.2 级别

| 级别 | 判断标准 |
|---|---|
| 阻断 | 可能反转上线、验收、风险、责任或重大状态决定。 |
| 主要 | 很可能导致范围、优先级、技术动作、业务影响或下一步被实质误解。 |
| 次要 | 局部语言、术语或一致性问题，决策影响有限。 |
| 建议 | 当前表达基本正确，仅为可选的可读性优化。 |

级别表示影响，不表示审核者信心。问题性质与级别必须分开。

## 五、误报控制

声明矛盾前逐项确认：

1. 是否是同一实体；
2. 是否是同一时间点；
3. 是否是同一版本；
4. 是否是同一环境；
5. 是否是同一范围或通道；
6. 是否是同一单位和分母；
7. 是否一个是快照、另一个是累计；
8. 分类是否互斥，是否允许同一记录多标签；
9. 是否混淆执行、通过、修复、验证、关闭和上线状态。

任何关键维度未写明时，优先归为“表达与理解风险”或“待作者确认”，而不是武断地判定已确认错误。

声明缺失前确认：

- 文档目的是否真的需要该信息；
- 信息是否存在于其他标题、表格、脚注或附件；
- 缺失是否阻止目标读者作出目标决定；
- 不把通用模板强加给有效的项目特定结构。

## 六、根问题合并

根问题身份优先使用：

```text
共同失败机制或共同根因 + 统一修正目标
```

证据位置、缺陷 ID、等级、通道、载体和各自验证动作是根问题下的“受影响实例”，用于证明和追踪，不作为拆分根问题的唯一依据。

规则：

1. 同一问题被多个岗位发现，只保留一个主问题项；
2. 总体结论只引用问题编号，不再次展开证据；
3. 待确认问题只写需要作者回答的决策点，并关联问题编号；
4. 不再输出“角色专项观察”重复问题；
5. 同一缺陷在正文和缺陷清单重复出现，只形成一个根问题，并在该问题下保留所有证据位置；
6. 多个缺陷同根因且修正目标一致时，可合并为一个根因级建议，但必须逐项保留每个独立缺陷 ID、等级、通道、载体和验证动作；
7. 多个缺陷虽然根因相同，但修正目标或验证方式实质不同时，可以拆成多个问题项，并说明共同根因关系；
8. 不得因为两个缺陷同根因，就擅自减少缺陷总数；
9. 低影响错别字可按同一修正规则合并；
10. 岗位没有独特问题时允许返回“无新增问题”。

## 七、最小引用与脱敏

正式报告只引用证明问题所需的最短片段。

默认需要脱敏：

- 实际验证码；
- 手机号、邮箱和账号；
- 姓名或个人标识；
- 完整经纬度；
- 通信码、动态令牌或认证值；
- 其他可能用于定位、认证或关联个人的数据。

脱敏示例：

- 验证码：`058323` → `05****`；
- 通信码：`ZJRKMW` → `ZJ****`；
- 坐标：保留“北纬/东经及符号格式”，不复制完整数值；
- 账号或设备号：保留必要前后缀，其余使用 `*`。

以下内容不是实际秘密，可按证据需要保留：

- `#code#`、`#name#`、`#lat#` 等模板占位符；
- 模板字段名；
- 缺陷 ID；
- 原文已有的系统名和公共技术缩写。

不要为了证明局部问题复制整行宽表格。

## 八、跨岗位理解比较

只有出现实质分歧时才输出比较表：

| 议题 | 专业基线 | 项目经理理解 | 研发负责人理解 | 产品/业务理解 | 风险 |
|---|---|---|---|---|---|

可报告的分歧满足至少一项：

- 存在两种由原文支持的合理理解；
- 某岗位无法识别状态、风险、责任或下一步；
- 不同理解会改变排期、修复、上线、验收或业务处置。

不能通过多数投票决定原文含义。

## 九、最终问题项

```markdown
### Q-01 问题标题

- **性质：** 已确认问题 / 表达与理解风险 / 待作者确认 / 覆盖限制
- **级别：** 阻断 / 主要 / 次要 / 建议
- **位置：** 标题路径 + 行号/页码/工作表与单元格
- **最小证据：** “必要原文”
- **问题与影响：** 精确说明失败机制及可能造成的错误决定或行动
- **影响岗位：** 仅列真实受影响岗位
- **统一修改建议：** 可执行的修改方向
- **安全改写：** 只有不改变事实时才提供；否则写“待作者确认后补写”
```

不允许使用“有些地方需要优化”等没有位置、证据和失败机制的空泛建议。

## 十、最终报告模板

```markdown
# 文档审核建议

## 一、审核边界
- 审核对象：
- 实际覆盖：
- 真源边界：
- 覆盖限制：仅在存在时填写

## 二、统一结论
- 可用性：可直接使用 / 修改后使用 / 暂不可用于决策
- 专业严谨性：
- 数据与前后一致性：
- 跨岗位理解一致性：
- 建议动作：

## 三、需优先处理的问题
[按级别排序的问题项]

## 四、跨岗位理解偏差
[仅在存在实质分歧时输出一张紧凑比较表]

## 五、待作者确认的事项
1. 【关联 Q-xx】精确问题

## 六、文字与术语修正
[合并低风险错别字、术语和可读性建议]
```

### 10.1 篇幅控制

- 1—5 段的短文：原则上不超过 5 个用户可见章节；
- 没有实质分歧时不输出岗位比较表；
- 没有待确认事实时不输出确认章节；
- 一个根问题只完整定义一次；
- 总结只引用问题编号，不重复论证；
- 不输出各岗位原始长篇复述；
- 完整性以覆盖所有实质风险为准，不以字数或角色数量为准。

## 十一、正式产物净化

交付前检查并清除内部过程信息：

- `eval`、`with_skill`、`old_skill`、`without_skill`；
- `grader`、`benchmark`、模型名和运行目录；
- “根据评测要求”等内部提示；
- 对话人格称呼；
- 英文审核 Schema 标签。

文件格式、系统名、代码字段、模板字段、缺陷 ID 和原文已有缩写不受此限制。
