# 中文两层测试文档审核

## 一、目标

审核的目标不是让多个角色分别写长篇意见，而是完成三件事：

1. 建立可靠的文档内部事实与专业判断基线；
2. 暴露项目、研发、产品等岗位从同一文字得到的不同理解；
3. 将所有证据合并为一份简洁、可执行、可追溯的中文审核建议。

重点检查：

- 数据、比例、状态、范围、日期、版本和结论是否内部一致；
- 测试逻辑、风险、完成条件和建议动作是否严谨；
- 专业术语、错别字、病句、指代和模糊表述是否存在问题；
- 不同岗位是否会对当前状态、风险、责任或下一步形成不同理解；
- 文档是否在保持专业准确的同时做到跨岗位可理解。

## 二、审核边界

### 2.1 默认是内部一致性审核

只有一份待审文档时，只能判断：

- 文档内部的数字能否闭合；
- 正文、表格和结论是否一致；
- 文档自己的证据是否支持自己的结论；
- 原文是否允许多个合理但不同的理解。

不得据此宣称真实系统、真实缺陷状态或真实业务数据正确或错误。

### 2.2 跨来源事实核验

只有用户明确指定某项资料为权威真源，或在审核前明确确认它是当前生效依据时，才执行跨源核验。可接受的真源包括：

- 原始测试执行记录；
- 需求或验收基线；
- 缺陷系统正式导出；
- 系统日志、接口响应或数据库查询结果；
- 用户明确指定为当前生效依据的配置或规则。

文件名相似、版本和时间看起来正式、内容措辞权威，都不能替代用户对真源身份的明确指定或确认。历史报告、审核者经验、常见模板和文档中未提供的引用资料，不自动视为真源。

执行跨源核验时，第一层必须逐项记录：待审文档位置、真源位置与版本、两者差异、差异对结论的影响，以及是否仍需作者确认。不得只给出“与真源不一致”而省略证据。

### 2.3 非目标

- 不从零创建测试文档；
- 不审核源代码；
- 不在缺少真源时验证外部事实；
- 不审计电子表格公式或重新计算工作簿；
- 不把语义审核扩展为纯版式、美工或视觉规范检查；
- 不为了让每个角色“有产出”而强行制造问题。

## 三、输入与源文件保护

接受一份待审文档，并可附带零个或多个由用户明确指定的权威真源。输入可以是文件路径或用户粘贴内容：

- `.md` / 纯文本；
- `.docx`；
- `.pdf`；
- `.xlsx`。

必须区分“待审文档”和“权威真源”，不能因为同时提供了多个文件就自行决定哪个文件优先。

审核前先读取 [references/format-routing.md](references/format-routing.md)；执行角色审核前读取 [references/review-rubric.md](references/review-rubric.md)。

源文件必须只读：

- 不覆盖、不批注、不接受修订、不重算、不重新保存；
- 记录路径、格式和实际可读范围；
- 需要保存审核报告时，写入新文件；
- 需要修改稿时，必须由用户另行明确要求并另存副本；
- 提取不完整时必须报告覆盖限制，不能把部分审核表述为完整审核。

## 四、工作流

## 第零步：建立位置感知事实台账

先提取原文事实，不急于下结论。至少整理：

- 文档目的、目标读者和请求作出的决定；
- 核心结论与建议；
- 测试范围、排除项、部分覆盖和未覆盖项；
- 数量、比例、单位、分母、日期、版本、环境和状态；
- 缺陷编号、等级、状态、载体和通道；
- 风险、责任人、下一步和完成条件；
- 重复出现的实体名、术语和引用资料；
- 可能需要脱敏的动态值。

每条事实记录准确位置、最小原文证据、归一化含义以及时间/版本/环境/范围等口径。事实台账是内部审核材料，不直接完整展示给用户。

长文档按章节、工作表或完整表格分块审核，最后必须执行一次全局一致性复核。不得只拼接局部摘要。

## 第一层：专业测试负责人审核

第一层建立专业基线，对以下内容负责：

1. **数据闭合**：总数与分项、比例与分母、正文与表格、缺陷数量与等级分布是否一致；
2. **逻辑严谨**：范围、执行状态、风险、结论和建议动作是否相互支持；
3. **专业性**：测试术语、指标、缺陷状态和质量结论是否准确且一致；
4. **状态边界**：是否混淆执行完成、测试通过、质量接受、缺陷修复、回归通过、工单关闭和允许上线；
5. **语言质量**：错别字、病句、悬空引用、术语漂移、指代不明和绝对化表达；
6. **证据边界**：哪些结论已经由文档内部证明，哪些必须等待作者或外部真源确认。

第一层内部输出“专业基线”：

- 文档意图；
- 当前状态；
- 主结论；
- 关键证据；
- 主要风险；
- 责任与下一步；
- 专业问题清单；
- 待确认事实。

专业基线不是最终报告中的独立长篇章节。

## 第二层：跨岗位独立理解审核

### 4.1 固定岗位

- 项目经理；
- 研发负责人；
- 产品经理或业务负责人。

当文档明确面向非专业人员、用户要求“通俗易懂”，或包含大量缩写、状态码、模板字段时，再增加“跨岗位可读性视角”。它是理解能力检查，不是组织岗位。

### 4.2 独立性

具备 Agent 工具时，所有第二层岗位必须在同一轮并行启动。每个岗位只接收：

- 同一份原文内容；
- 同一份位置映射；
- 自己的角色契约。

在独立复述完成前，不得看到第一层专业基线或其他岗位的意见，避免被答案诱导。

Agent 不可用时，只能降级为顺序角色视角复核：每次重置角色说明，并尽量不主动引用前一个岗位的结果，但同一上下文无法保证完全独立。最终报告必须在“审核边界”中披露该降级，不能把它表述成与独立 Agent 等价的多人审核。

### 4.3 每个岗位先回答

1. 文档要解决什么问题？
2. 当前处于什么状态？
3. 主要结论是什么？
4. 最关键的依据是什么？
5. 主要风险或影响是什么？
6. 谁应当在什么条件下采取什么行动？
7. 文档希望本岗位作出什么决定？

角色边界和内部返回结构以 `review-rubric.md` 为准。

## 第三步：比较专业基线与岗位理解

所有第二层复述完成后，再与第一层专业基线比较：

- 岗位理解是否与专业含义一致；
- 是否出现由原文支持的另一种合理理解；
- 是否有人无法识别当前状态、风险、责任或下一步；
- 分歧是否会改变排期、修复、验收、上线或业务处置。

少数岗位的合理误解也是证据，不能通过多数投票删除。只有会造成实质决策或行动差异的分歧才进入最终报告。

## 第四步：综合与裁决

综合者不是第五个审核角色，不重新发明事实。按以下顺序裁决：

1. 精确原文、算术关系和用户指定真源优先；
2. 先确认实体、时间、版本、环境、范围、单位和分母是否相同；
3. 第一层有充分证据的专业判断作为语义基线；
4. 第二层提供了第一层遗漏的精确证据时，退回第一层复核；
5. 合理的岗位误解保留为“表达与理解风险”；
6. 无法从文档恢复作者意图时列为“待作者确认”；
7. 同一根问题合并一次，但保留所有独立缺陷编号、等级、通道和影响位置；
8. 通俗化不得改变已确认的数字、范围、状态、专业术语和结论。

## 五、最终报告

默认只在对话中输出；用户要求保存时，写入新的审核报告文件，不覆盖源文件。

报告使用以下结构，空章节省略：

```markdown
# 文档审核建议

## 一、审核边界
## 二、统一结论
## 三、需优先处理的问题
## 四、跨岗位理解偏差
## 五、待作者确认的事项
## 六、文字与术语修正
```

每个实质问题只完整说明一次，字段和示例见 `review-rubric.md`。

### 输出约束

- 正式标题、字段、分类、级别和建议全部使用中文；
- 文件扩展名、系统名、模板字段、缺陷 ID 和原文已有缩写可保留；
- 不输出各角色的长篇原始报告；
- 总体结论只点名问题编号，不重复完整证据；
- 没有真实理解差异时省略“跨岗位理解偏差”；
- 没有待确认事项时省略该章节；
- 短文档必须得到短报告，不生成流程档案式长文；
- 不在正式报告中出现评测目录、模型、grader、benchmark、with_skill 等内部信息；
- 对话称呼不得进入交付报告正文；
- 敏感数据只做最小引用并按 `review-rubric.md` 脱敏。

## 六、澄清与后续修改

以下待确认事项会改变数字、范围、状态、责任、风险或结论时：

- 先输出审核建议和精确问题；
- 不擅自选择一个方便的答案；
- 用户未澄清时，用【待确认】占位；
- 只有用户明确要求修改文档后，才生成独立修改稿；
- 修改完成后只做一次轻量复审，检查是否引入新矛盾或改变事实。

## 七、完成标准

审核完成必须满足：

- 可读范围已明确；
- 全局一致性复核已执行；
- 每个实质问题都有准确位置和最小证据；
- 专业基线与第二层岗位复述先独立产生、后比较；
- 未越过真源边界；
- 同一根问题只定义一次；
- 独立缺陷、等级、通道和载体未被误删；
- 最终只有一份中文统一审核建议；
- 敏感动态值未被无必要地复制；
- 源文件保持不变。
