# US-017 管理账户内设备分组
> 口径依据：大纲第 4.5、4.10、8 章。海外版构建分组名为 1～40 字符，国内版构建为 1～15 字符，不随界面语言变化；新增与重命名使用相同上限，名称须含非空白字符，首尾空格原样保留，同一账户跨层级精确判重，不同账户名称隔离。

## [P4] 验证海外版构建跨中英文界面的新增重命名边界与精确提示
- 测试类型
  - 功能
- 前置条件
  1. 安装同一海外版产品构建，personal10 名下有一级组「海外旧名」
  2. 账户内不存在「A」「1234567890123456789012345678901234567890」
- 测试步骤
  1. 中文界面打开新增弹窗，核对提示后创建 1 字符名称「A」。
  2. 切换英文界面打开新增弹窗，创建 40 字符名称「1234567890123456789012345678901234567890」。
  3. 英文界面打开「海外旧名」重命名弹窗，改为 40 字符名称「abcdefghijklmnopqrstuvwxyz1234567890ABCD」。
  4. 新增或重命名时输入 41 字符名称「12345678901234567890123456789012345678901」并保存。
- 预期结果
  1. 新增弹窗精确显示 `Group name (1–40 characters)`，「A」创建成功。
  2. 切换界面语言后仍精确显示 `Group name (1–40 characters)`，40 字符名称完整保存。
  3. 重命名弹窗同样精确显示 `Group name (1–40 characters)`，40 字符重命名成功。
  4. 41 字符在新增和重命名均被拦截，不因中文或英文界面改变海外版 40 字符上限。

## [P4] 验证国内版构建跨中英文界面的新增重命名边界
- 测试类型
  - 功能
- 前置条件
  1. 安装同一国内版产品构建，personal11 名下有一级组「国内旧名」
  2. 账户内不存在「123456789012345」和「ABCDEFGHIJKLMNO」
- 测试步骤
  1. 英文界面新增 15 字符名称「123456789012345」。
  2. 英文界面新增 16 字符名称「1234567890123456」。
  3. 切换中文界面，将「国内旧名」重命名为 15 字符名称「ABCDEFGHIJKLMNO」。
  4. 中文界面将该组重命名为 16 字符名称「ABCDEFGHIJKLMNOP」。
- 预期结果
  1. 15 字符新增成功，英文界面不会套用海外版 40 字符上限。
  2. 16 字符新增被拦截并提示国内版 1～15 字符范围。
  3. 15 字符重命名成功，中文界面与英文界面使用相同国内版上限。
  4. 16 字符重命名被拦截，正式名称仍为「ABCDEFGHIJKLMNO」。

## [P3][反向] 验证正常 UI 与绕过 UI 均禁止空名称和纯空格名称
- 测试类型
  - 功能
- 前置条件
  1. personal10 已打开新增一级组弹窗，并具备抓取新增请求及直接调用服务端新增分组接口的测试条件
- 测试步骤
  1. 在正常 UI 中名称留空并点击保存。
  2. 在正常 UI 中输入原始值「␠␠␠」并点击保存，其中每个 ␠ 表示一个 U+0020 空格，记录客户端是否发出请求及服务端结果。
  3. 绕过 UI，直接调用新增分组接口提交长度 3、三个字符均为 U+0020 的名称「␠␠␠」。
  4. 查询 personal10 分组主数据的新增记录。
- 预期结果
  1. 空名称校验失败，弹窗保留且不产生有效新增；可由客户端直接拦截。
  2. 纯空格名称可由客户端拦截而不发请求，也可提交后由服务端拒绝；正常 UI 不强制必须发出请求，但任何路径均不得保存成功。
  3. 绕过 UI 的接口请求被服务端明确拒绝，证明服务端独立校验名称至少包含一个非空白字符。
  4. 三次操作均未新增真实分组，也未产生空名称或纯空格名称的 groupId。

## [P1] 验证首尾空格原样保留且大小写和全部空格参与比较
- 测试类型
  - 功能
- 前置条件
  1. personal10 已存在一级组「Ranch A」
  2. personal10 尚不存在「ranch a」「Ranch␠␠A」「␠Ranch A␠␠」，其中 ␠ 表示一个 U+0020 空格
- 测试步骤
  1. 创建一级组「ranch a」。
  2. 创建原始值「Ranch␠␠A」。
  3. 创建原始值「␠Ranch A␠␠」。
  4. 查询三个新增请求与服务端正式名称的长度、首字符和尾字符。
- 预期结果
  1. 大小写差异参与比较，「ranch a」创建成功。
  2. 内部两个 U+0020 空格原样保存，该名称长度为 8。
  3. 首部一个、尾部两个 U+0020 空格原样保存，该名称长度为 10，不被裁剪成「Ranch A」。
  4. 三个请求值与正式值逐字符一致，四个近似名称分别对应四个 groupId。

## [P3][反向] 验证新增一级分组服务端失败时保留输入并可重试
- 测试类型
  - 可靠性
- 前置条件
  1. 海外版账号 personal14 当前不存在分组「服务失败测试组」
  2. 服务端可将第一次新增请求返回 HTTP 500 和可读原因「分组服务暂时不可用」，第二次请求成功
- 测试步骤
  1. 打开新增弹窗输入「服务失败测试组」并保存。
  2. 等待第一次请求失败，核对弹窗、输入值和分组主数据。
  3. 不重新输入名称，直接点击重试保存。
  4. 查询第二次请求结果和正式分组记录。
- 预期结果
  1. 第一次请求使用原始名称提交，不提前关闭弹窗或插入本地正式分组。
  2. 失败后弹窗保持打开，输入仍为「服务失败测试组」，页面展示服务端可读原因且正式数据未新增。
  3. 重试继续提交同一原始名称，不变为空值或其他缓存名称。
  4. 仅第二次成功后创建一条真实一级分组并关闭弹窗，不产生重复 groupId。

## [P3][反向] 验证达到服务端分组数量上限时不写死产品上限
- 测试类型
  - 功能
- 前置条件
  1. 测试环境为 personal15 配置分组总量上限 groupLimit=3，仅作为测试夹具，不代表产品固定上限
  2. personal15 当前已存在 3 个真实分组，APP 未内置固定分组数量常量
- 测试步骤
  1. 输入合法名称「第四测试组」并提交新增。
  2. 检查请求是否到达服务端及返回的限制字段。
  3. 将测试配置调整为 groupLimit=4 后使用同一合法名称再次提交。
  4. 查询正式分组数量和页面提示。
- 预期结果
  1. APP 可正常提交合法名称，由服务端当前配置决定容量结果。
  2. 首次请求因 groupLimit=3 被拒绝并显示可读的分组数量上限原因，不新增分组。
  3. 配置调整后相同客户端不需发版即可成功创建「第四测试组」。
  4. 正式分组数量变为 4，证明 APP 未写死 3、15、40 等未确认数量上限。
