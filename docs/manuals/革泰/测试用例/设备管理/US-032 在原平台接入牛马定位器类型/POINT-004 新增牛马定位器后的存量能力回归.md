# US-032 在原平台接入牛马定位器类型
> 口径依据：设备管理逻辑大纲第 3.1～3.4、6.1、7、9～10 节。新增类型不得改变旧设备类型的原绑定规则、旧多边形围栏、原告警同步和原历史分页；APP 对不支持类型仍按既定入口规则处理。

## [P1] 验证旧设备类型沿用原平台绑定规则
- 测试类型
  - 兼容性
- 前置条件
  1. 旧类型北斗设备 DEV-OLD-14001 已在管理后台入库，设备卡号为 OLD14001001
  2. 个人账号 GT-P-1411 在监控平台 Web 具备旧类型原有绑定资格且配额充足
  3. DEV-OLD-14001 未被其他个人账号占用个人绑定槽位
- 测试步骤
  1. 在监控平台 Web 以 GT-P-1411 按原入口绑定 OLD14001001。
  2. 查询 GT-P-1411 的设备关系、设备列表和设备总数。
  3. 在 APP 以 GT-P-1411 从“绑定设备”输入 OLD14001001。
  4. 再次查询 Web 中 DEV-OLD-14001 的绑定关系和数量。
- 预期结果
  1. 旧类型按上线前原平台规则绑定成功，新增牛马定位器类型未改变旧入口、配额和同类槽位行为。
  2. 仅新增 1 条 GT-P-1411 的个人直接绑定关系，Web 列表按设备唯一标识显示 1 台。
  3. APP 明确识别设备已入库但类型不受当前 APP 绑定入口支持，不误提示设备不存在，也不新增第二条关系。
  4. 原绑定关系保持 1 条，设备总数不增加，APP 的新类型接入逻辑未反向改写旧类型绑定数据。

## [P1] 验证旧多边形围栏判定与关系保持原结果
- 测试类型
  - 兼容性
- 前置条件
  1. 旧类型设备 DEV-OLD-14002 已绑定上线前创建的多边形安全区 GF-POLY-14001
  2. GF-POLY-14001 的原顶点、设备关系和判定基线已保存，并留存上线前同组回归结果
  3. 已准备位于多边形内部的有效位置 POLY-IN-14001 和外部的有效位置 POLY-OUT-14001
- 测试步骤
  1. 新类型功能上线后查询 GF-POLY-14001 的围栏主数据、设备关系和判定基线。
  2. 让 DEV-OLD-14002 上报 POLY-IN-14001 并查询判定结果。
  3. 让 DEV-OLD-14002 上报 POLY-OUT-14001 并查询判定结果与事件。
  4. 将本次围栏关系、内外判定和事件结果与上线前同组回归结果对比。
- 预期结果
  1. 旧多边形顶点、设备关系和既有基线均未被迁移、清空或转换为新类型专属结构。
  2. POLY-IN-14001 仍按原多边形规则判定为内部，不因新增类型改变边界算法或坐标口径。
  3. POLY-OUT-14001 仍按原规则判定为外部，并按原基线与事件规则处理，不走牛马定位器专属分支。
  4. 本次结果与上线前基线一致，未出现关系复制、事件漏记、重复事件或围栏类型变化。

## [P1] 验证旧设备原告警同步和告警入口不回归
- 测试类型
  - 可靠性
- 前置条件
  1. 旧类型设备 DEV-OLD-14003 对账号 GT-E1-1413 可见且当前在线
  2. 监控平台、APP 告警模块和管理后台可查询同一设备告警记录
  3. DEV-OLD-14003 当前无未处理告警
- 测试步骤
  1. 按旧设备原告警触发方式生成告警事件 ALARM-OLD-14001。
  2. 查询管理后台和监控平台中的事件身份、设备身份、发生时间和处理状态。
  3. 在 APP 告警模块查询 ALARM-OLD-14001，并查看设备列表中的 DEV-OLD-14003 状态。
  4. 在 APP 设备卡片更多菜单和详情抽屉检查告警入口。
- 预期结果
  1. 原告警链只生成 1 条 ALARM-OLD-14001，不因新增设备类型重复路由或漏同步。
  2. 两端查询到同一事件和 DEV-OLD-14003，发生时间与处理状态一致。
  3. APP 告警模块可按当前账号权限查询该事件，设备列表展示告警并保留在线底层差异。
  4. 设备更多菜单和详情抽屉仍不提供单设备告警记录入口；入口调整不删除历史告警或改变告警中心查询能力。

## [P1] 验证旧设备历史记录分页不重不漏
- 测试类型
  - 兼容性
- 前置条件
  1. 旧类型设备 DEV-OLD-14004 对账号 GT-E1-1414 可见
  2. DEV-OLD-14004 已存在 45 条连续历史记录，记录身份为 HIST-OLD-14001 至 HIST-OLD-14045
  3. 45 条记录的时间和排序结果已在新类型上线前固化为回归基线
- 测试步骤
  1. 以 GT-E1-1414 打开 DEV-OLD-14004 的原历史记录页面并获取第一页。
  2. 按页面返回的下一页标识连续加载，直至没有下一页。
  3. 汇总各页记录身份，检查总数、重复项、缺失项和跨页顺序。
  4. 将完整分页结果与上线前 45 条回归基线对比。
- 预期结果
  1. 第一页按原历史查询契约返回，不切换到新类型独立查询入口或独立事实库。
  2. 每次加载均承接上一页位置，最终正常结束，不出现循环页、跳页或提前终止。
  3. 共取得 HIST-OLD-14001 至 HIST-OLD-14045 的 45 条唯一记录，无重复、无缺失，跨页排序稳定。
  4. 分页字段含义、记录范围和顺序与上线前基线一致，新增牛马定位器未改变旧历史分页默认行为。

## [P1] 验证旧设备指令链沿用原协议与记录基线
- 测试类型
  - 兼容性
- 前置条件
  1. 旧类型设备 DEV-OLD-14005 对账号 GT-E1-1415 可见，并具备上线前原指令入口与原协议路由
  2. 已固化原指令夹具 CMD-OLD-14001、参数基线 PARAM-OLD-14001、成功反馈基线 FEEDBACK-OLD-14001 及对应记录字段基线
  3. 测试环境可观察原协议处理链、新类型专属适配边界和指令记录数，提交前不存在 CMD-OLD-14001 记录
- 测试步骤
  1. 以 GT-E1-1415 从旧设备原指令入口提交 CMD-OLD-14001，并核对实际协议路由与下发参数。
  2. 观察任务从受理到写出的四态变化和记录创建情况。
  3. 通过旧协议链返回 FEEDBACK-OLD-14001，再查询任务反馈、设备关联和指令记录。
  4. 将本次参数、状态、反馈与记录结果同上线前基线逐项比较，并检查新类型专属适配调用与重复记录。
- 预期结果
  1. CMD-OLD-14001 继续进入旧设备原协议处理链，实际参数与 PARAM-OLD-14001 基线一致，不进入牛马定位器专属适配边界。
  2. 状态仍按原链路使用统一 SENDING、SENT、FAILURE、CANCEL 四态；本次正常写出按基线从 SENDING 推进为 SENT，不新增协议专属状态。
  3. FEEDBACK-OLD-14001 按原关联规则回写同一任务记录，反馈内容、时间和设备身份与基线一致，不另建新类型事实或记录链。
  4. 最终仅保留 1 条 CMD-OLD-14001 业务记录，参数、状态、反馈和记录字段与上线前基线一致，无新适配误路由、重复下发或重复记录。
