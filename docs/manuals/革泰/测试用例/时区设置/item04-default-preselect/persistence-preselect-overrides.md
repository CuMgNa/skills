# 用户故事：持久化带出与预选覆盖

> 口径依据：大纲第 6 章。再次登录（本设备本账号有记录）带出上次保存值；本页修改后下次登录带出新值；已有保存值时，登录页带出保存值而非当前系统时区（系统时区变更不覆盖已存配置）。

## [P2] 验证再次登录带出上次保存值而非系统时区
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录过，保存时区为 Tokyo
  2. 手机系统时区在退出登录后改为 Asia/Dubai（GMT+4:00）
- 测试步骤
  1. 系统时区改为 Dubai 后，打开 APP 到登录页，查看时区项预选值。
  2. 提交登录，进入「我的 → 时区设置」查看选中行。
- 预期结果
  1. 登录页带出已保存值 Tokyo（不是新系统时区 Dubai）——本设备本账号有记录时以上次保存值为准。
  2. 选中行为 Tokyo，系统时区变更不覆盖已存配置。

## [P2] 验证连续修改后重登带出最终值
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，当前时区 Beijing
- 测试步骤
  1. 当天先改选 Perth，再改选 Adelaide，最后改选 Kiritimati Island（GMT+14:00）。
  2. 退出登录后重新登录。
  3. 进入「我的 → 时区设置」查看选中行。
- 预期结果
  1. 三次改选均成功。
  2. 登录成功。
  3. 选中行为 Kiritimati Island（带出最终值，中间值 Perth / Adelaide 不残留）。

## [P2] 验证登录页改选时区后提交登录配置为改选值
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录过，保存时区为 Beijing
  2. 登录页当前带出 Beijing
- 测试步骤
  1. 在登录页把时区项从 Beijing 改选为 Seoul。
  2. 提交登录。
  3. 进入「我的 → 时区设置」查看选中行，并查看资料页时区行。
- 预期结果
  1. 登录页改选成功。
  2. 登录成功。
  3. 选中行与资料页均为 Seoul——登录页选择即本账号时区，覆盖旧保存值。

## [P4] 验证冷启动时区配置在首个业务页渲染前就绪（首帧闪变）
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，保存时区为 Kiritimati Island（GMT+14:00），与系统时区 Asia/Shanghai 差 6 小时
  2. 监控页有当天定位上报数据（展示值跨日）
- 测试步骤
  1. 杀进程后冷启动 APP。
  2. 录屏观察从启动到监控页首帧渲染完成的过程中「最近更新时间」的展示。
  3. 逐帧回放检查首帧时间值。
- 预期结果
  1. 冷启动正常。
  2. 启动过程无卡顿、无崩溃。
  3. 首帧即为 Kiritimati 口径（+14）展示，无「先按 Beijing 渲染再跳变为 +14」的首帧闪变（开发契约 #9：时区配置读取须在首个业务页渲染前就绪）。
