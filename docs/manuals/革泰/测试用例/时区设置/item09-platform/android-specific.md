# 用户故事：Android 平台专项

> 口径依据：大纲 12A.1 章。返回栈缓存页失效重渲染；系统时区运行中变更（ACTION_TIMEZONE_CHANGED）不得改写 APP 配置；Auto Backup / 换机克隆两条换机路径分别断言；工作资料 / 应用分身双开存储独立；Doze 下自动刷新精度归 US-030（指针引用不展开）。

## [P2] 验证系统时区运行中变更不改写 APP 时区配置（A2）
- 测试类型
  - 兼容性
- 前置条件
  1. Android 测试机，账号 testuser01 已登录，APP 时区为 Tokyo，APP 在前台监控页
  2. 准备将系统时区从 Asia/Shanghai 改为 America/New_York
- 测试步骤
  1. 记录当前监控页「最近更新时间」展示口径。
  2. 切到系统设置，将系统时区改为 America/New_York（触发 TIMEZONE_CHANGED 广播）。
  3. 回到 APP 前台（不重启），查看监控页时间展示口径与时区设置页选中行。
  4. 再将 APP 切后台 5 分钟后回前台复查。
- 预期结果
  1. 记录成功（Tokyo 口径）。
  2. 系统时区变更成功。
  3. 监控页仍按 Tokyo 口径展示、选中行仍为 Tokyo（APP 配置不得被系统广播改写），不崩溃、列表不错乱。
  4. 回前台后仍维持 Tokyo 口径，全程无跳变。

## [P3][反向] 验证存储健壮性与升级迁移（契约 #10/#11）
- 测试类型
  - 可靠性
- 前置条件
  1. Android 测试机，账号 testuser01 已登录，时区为 Beijing
  2. 有手段构造本地存储异常（与开发约定的调试入口 / root 写入非法 IANA 值如 `Invalid/Zone_Name`）
- 测试步骤
  1. 将本地存储的时区值改为非法值 `Invalid/Zone_Name`。
  2. 杀进程冷启动 APP。
  3. 查看启动状态与「我的 → 时区设置」选中行。
  4. 构造历史版本偏移量格式（如存储 `8.0`），重走步骤 2-3（升级迁移取证）。
- 预期结果
  1. 构造成功。
  2. 启动正常，不崩溃、启动链路不因时区解析失败阻断。
  3. 回退默认（系统时区）并允许重选（契约 #10）。
  4. 偏移量旧格式被一次性迁移或回退兜底，不出现崩溃或选中项凭空消失。

## [P4] 验证存储 IANA 值不在 138 精选列表时的兜底展示（场景 16）
- 测试类型
  - 功能
- 前置条件
  1. Android 测试机，账号 testuser01 已登录
  2. 有手段将本地存储时区改为 `Etc/GMT+5`（系统映射失败类值，不在 138 列表）
- 测试步骤
  1. 将本地存储时区值改为 `Etc/GMT+5`。
  2. 杀进程冷启动 APP，进入「我的 → 时区设置」。
  3. 查看选中项展示与列表状态。
  4. 改选一个正常列表项（如 Seoul），退出重进确认恢复。
- 预期结果
  1. 构造成功。
  2. 页面正常打开，不崩溃。
  3. 选中项不凭空消失：回退展示该 IANA 原名或偏移兜底行（回退策略待联调 #11，行为如实记录）。
  4. 改选 Seoul 后配置恢复正常，选中行清晰可见。

## [P5] 验证 Doze / 后台限流下自动刷新不精确仅指针引用（A5）
- 测试类型
  - 可靠性
- 前置条件
  1. Android 测试机（可进入 Doze），账号已登录，监控页 30s 自动刷新开启
- 测试步骤
  1. 使设备进入 Doze 模式，APP 留后台 10 分钟。
  2. 回前台观察监控页时间刷新行为。
  3. 判定口径按 US-030 在线刷新间隔边界执行（本用例仅确认时区展示不因 Doze 错乱）。
- 预期结果
  1. Doze 进入成功。
  2. 回前台后按 APP 时区正常重渲染，无旧时区 / 错乱时区残留。
  3. 刷新间隔精度问题不在本篇判定，指针引用 US-030。
