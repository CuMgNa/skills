# 用户故事：今日窗口按 APP 时区计算与错位断言

> 口径依据：大纲第 8 章、结论 15。一切「今天」概念按 APP 时区而非系统时区计算：日历高亮「今天」、日期选择器 min-date、今日查询窗口全部按 APP 时区算；同一物理时刻可出现三种「今日」（北京 09-18 23:30 时选 Kiritimati(+14) → APP 今日 = 09-19；选 UTC-11 → 今日 = 09-17）。

## [P1] 验证同一物理时刻三种「今日」按 APP 时区各自正确
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，手机系统时区固定为 Asia/Shanghai
  2. 选择执行时点：北京时间 2026-09-24 18:30（= UTC 10:30，此窗口内 -11/+8/+14 三区日期互异，勿改系统时区）
- 测试步骤
  1. APP 时区保持 Beijing，打开轨迹日历查看「今天」高亮日期。
  2. 改选 Kiritimati Island（GMT+14:00），重进轨迹日历查看「今天」高亮。
  3. 改选 Coordinated Universal Time-11（GMT-11:00，若列表含纯偏移占位行；否则跳过此步并在用例记录中注明占位条目未上线的取证结论），重进日历查看「今天」高亮。
- 预期结果
  1. Beijing 口径「今天」= 09-24（UTC 10:30 + 8 = 18:30 当日）。
  2. +14 口径「今天」= 09-25（UTC 10:30 + 14 = 次日 00:30）。
  3. -11 口径「今天」= 09-23（UTC 10:30 - 11 = 前一日 23:30）——同一物理时刻三种「今日」（09-23 / 09-24 / 09-25）并存，全部按 APP 时区计算，不得偷懒用系统时区。

## [P2] 验证日期选择器 min-date（今天下限）按 APP 时区计算
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，系统时区 Asia/Shanghai
  2. 执行时点：北京时间 2026-09-24 23:30
- 测试步骤
  1. APP 时区选 Kiritimati Island（GMT+14:00）。
  2. 打开轨迹日期选择器，查看可选日期下限（min-date）。
  3. 尝试选择下限前一天日期。
- 预期结果
  1. 改选成功。
  2. min-date 为 2026-09-25（+14 口径的「今天」，契约 #13）。
  3. 09-24 不可选（灰置或拦截），下限按 APP 时区计算。

## [P2] 验证会话中途切时区后「今日」查询窗口随新时区重算
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，当前时区 Beijing
  2. 执行时点：北京时间 D 日 23:30，已注入「明天」性质边界点：UTC D 15:30（北京 D 23:30 = Kiritimati D+1 日 05:30）
- 测试步骤
  1. Beijing 口径轨迹页查「今日」，确认不含该边界点，记录点数。
  2. 改选 Kiritimati Island，重进轨迹页保持「今日」筛选。
  3. 查看点集变化。
- 预期结果
  1. Beijing「今日」不含该点。
  2. 查询窗口随新时区重算。
  3. 「今日」点集多出该「明天」的点（+14 口径已是 D+1 日）——症状「日头新时区、点数旧窗口」即缺陷（窗口-展示同源断言，10.3 节抓手）。

## [P4] 验证通知栏时间与 APP 内时间分层展示
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，APP 时区为 London，系统时区为 Asia/Shanghai
  2. 设备有告警推送（发生时刻北京 2026-09-24 18:00 = 伦敦夏令 11:00）
- 测试步骤
  1. 收到告警推送，查看系统通知栏显示的时间。
  2. 打开 APP 进告警页查看同一条告警的发生时间。
  3. 比较两者。
- 预期结果
  1. 通知栏按系统时区显示 18:00（OS 格式化）。
  2. APP 内按 APP 时区显示 11:00（London 夏令 +1）。
  3. 两者相差 7 小时属设计使然（通知栏系统时区 / APP 内 APP 时区分层），通知栏时间不作为 APP 时区 bug 证据。
