# 用户故事：服务端校时基准

> 口径依据：大纲第 8 章、结论 15、第 11 章场景 19、契约 #12。今日 / 昨日 / 日历 / min-date 的一切「当前时刻」以服务端校时结果为基准（登录 / 刷新时校时），不得取设备本地时钟——用户手改手机日期不得影响日期边界；设备时钟偏差超阈值的提示策略待联调（#10）。

## [P1] 验证设备时钟手改拨快数天后今日边界不漂移
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，APP 时区 Beijing，网络正常
  2. 真实服务端日期为 2026-09-24
- 测试步骤
  1. 将手机系统日期手动改为 2026-10-01（拨快 7 天），保持网络开启。
  2. 回到 APP 下拉刷新监控页，打开轨迹日历查看「今天」高亮。
  3. 查看轨迹页「今日」筛选的查询窗口覆盖日期。
  4. 打开日期选择器查看 min-date。
- 预期结果
  1. 系统日期改为 10-01 成功。
  2. 日历「今天」仍高亮 2026-09-24（以服务端校时为「现在」，不随设备时钟漂移）。
  3. 「今日」查询窗口仍为服务端日期 09-24 口径。
  4. min-date 仍为 09-24，不因设备拨快变为 10-01。

## [P2] 验证设备时钟拨慢数天后昨日 / 日历边界不漂移
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，APP 时区 Beijing，网络正常，真实服务端日期 2026-09-24
  2. 昨日（09-23）有轨迹数据
- 测试步骤
  1. 将手机系统日期手动改为 2026-09-20（拨慢 4 天）。
  2. 回到 APP 下拉刷新，轨迹页查「昨日」筛选结果。
  3. 核对结果覆盖的日期窗口。
- 预期结果
  1. 系统日期修改成功。
  2. 「昨日」查询正常返回。
  3. 窗口为服务端口径的 09-23（不是设备日期 09-19 的昨日）——「现在」始终取服务端时间。

## [P3][反向] 验证飞行模式（无校时数据）下的降级行为记录
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录后进入飞行模式
  2. 手机系统日期被手改为 2026-10-01（服务端真实 09-24）
- 测试步骤
  1. 飞行模式下杀进程重开 APP。
  2. 查看轨迹日历「今天」高亮与「今日」查询窗口。
  3. 恢复网络下拉刷新后复查。
  4. 将观察到的降级取值（服务端缓存时刻 / 设备时钟兜底）记录为取证结论，供联调对齐（待确认 #10）。
- 预期结果
  1. APP 正常打开，不崩溃。
  2. 无新校时数据时行为如实记录（允许暂用上次校时缓存；不得因无校时而功能不可用）。
  3. 恢复网络刷新后回到服务端口径 09-24。
  4. 降级口径记录完整，作为与开发 / 产品对齐偏差提示策略的输入。
