# 用户故事：APP 时区与设备 ZONE 指令互不影响（防混淆金用例）

> 口径依据：大纲第 9 章、结论 1/12。两个「设置时区」功能分别管理、互不代替、互不影响：APP 展示时区是纯本地展示层配置（不是指令、无记录、无失败场景）；设备 ZONE 指令是走指令链路的设备协议侧设置（产生指令记录）。反向断言金用例：改 APP 时区 → 指令记录页不出现任何新记录；下发 ZONE → APP 展示时区纹丝不动。ZONE 指令自身链路（提交→投递→设备回复）归指令篇 7.3，不在本篇展开。

## [P1] 验证修改 APP 时区不产生任何指令记录
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，当前时区 Beijing
  2. 指令记录页当前记录数为 5 条
  3. 名下设备在线
- 测试步骤
  1. 进入「我的 → 时区设置」，依次改选 Sydney、Tokyo、Hawaii 三个时区。
  2. 进入「指令 → 指令记录」页查看记录列表。
  3. 核对记录条数与内容。
- 预期结果
  1. 三次改选均即时生效。
  2. 指令记录页正常打开。
  3. 记录数仍为 5 条，无任何新增——改 APP 时区不是指令、不下发任何内容、不产生指令记录（防混淆金用例）。

## [P1] 验证下发设备 ZONE 指令后 APP 展示时区不变
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，APP 时区为 Beijing，设备在线
  2. 记录当前监控页「最近更新时间」的展示口径（+8）
- 测试步骤
  1. 通过「指令 → 参数设置 → 设置设备时区」下发一条设备 ZONE 指令（如 UTC+10:00），等待设备回复确认。
  2. 返回 APP 监控页，查看「最近更新时间」展示口径。
  3. 进入「我的 → 时区设置」查看选中行。
  4. 进入指令记录页确认该 ZONE 指令有记录。
- 预期结果
  1. 指令下发成功、设备回复确认（指令链路细节按指令篇断言）。
  2. 监控页时间仍按 Beijing（+8）展示，纹丝不动。
  3. 选中行仍为 Beijing——下发 ZONE 不改 APP 展示时区。
  4. 指令记录页出现该 ZONE 指令记录（与 APP 时区配置的「无记录」形成体例对照）。

## [P2] 验证两个功能的入口与取值体系互相独立
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，APP 时区为 Kathmandu（GMT+5:45）
- 测试步骤
  1. 打开「指令 → 参数设置 → 设置设备时区」，查看该入口的可选值形态。
  2. 对比「我的 → 时区设置」列表的可选值形态。
  3. 在设备 ZONE 入口选择一个与 Kathmandu 无关的值（如协议侧 UTC+08:00）提交。
  4. 回「我的 → 时区设置」查看选中行。
- 预期结果
  1. ZONE 入口取值为终端协议支持的 UTC 偏移枚举（由服务端 / 协议能力下发）。
  2. APP 时区列表为 IANA 区域名 138 项精选视图——两套取值体系不同。
  3. ZONE 指令提交走指令链路。
  4. 选中行仍为 Kathmandu（+5:45 这类非整点档在协议偏移枚举中甚至不可表达），互不影响。

## [P3][反向] 验证 APP 时区无失败场景与 ZONE 失败场景体例不同
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，网络正常
  2. 名下设备离线（构造 ZONE 指令失败环境）
- 测试步骤
  1. 进入「我的 → 时区设置」改选 Guam, Port Moresby（GMT+10:00）行。
  2. 向离线设备下发 ZONE 指令，观察指令失败链路表现（拒发 / 待投递）。
  3. 对比两者交互形态。
- 预期结果
  1. 时区改选成功（纯本地写入，无网络请求、无失败场景、无保存失败回弹）。
  2. ZONE 指令出现失败 / 待投递形态（指令失败链路，细节按指令篇）。
  3. 两者体例不同：时区无失败场景，指令有完整失败链路——用例不得互相套用。
