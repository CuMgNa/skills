# 用户故事：纯日期不跨日与指令排序键不变

> 口径依据：大纲 7.3 节、第 11 章场景 10/11、结论 11/13。服务到期日等纯日期字段按业务日期原样展示，不做 UTC 零点换算（PRD 既定）；切换时区只改指令历史展示时间，「下发时间 = 首次提交时刻」排序键不变、补发不置顶（US-034 关联边界）。

## [P1] 验证服务到期日等纯日期字段不因时区跨日
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，当前时区 Beijing
  2. 名下设备服务到期日为 2027-03-15，物联网卡有效期为 2027-06-30 至 2028-06-29
- 测试步骤
  1. 在 Beijing 口径下记录设备页服务到期日、卡有效期起止的展示。
  2. 改选 Kiritimati Island（GMT+14:00，与 +8 差 6 小时，必然跨日）。
  3. 重进设备页查看服务到期日与卡有效期。
  4. 再改选 International Date Line West（GMT-12:00），重进设备页复查。
- 预期结果
  1. 记录展示值为 2027-03-15 与 2027-06-30 至 2028-06-29。
  2. 改选成功。
  3. 纯日期字段仍显示 2027-03-15、2027-06-30 至 2028-06-29，不跨到前一日 / 后一日（纯日期不跨日，PRD 既定）。
  4. -12 偏移下同样不跨日，原样展示。

## [P1] 验证切换时区后指令历史排序不变
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，当前时区 Beijing
  2. 指令记录页已有 5 条记录，按提交时间先后为 R1 至 R5（R1 最早）
- 测试步骤
  1. Beijing 口径下记录指令列表顺序（R1…R5）与各条展示时间。
  2. 改选 Hawaii（GMT-10:00）。
  3. 重进指令记录页查看列表顺序与展示时间。
  4. 找一条历史指令（如 R3）触发补发，重进列表查看顺序。
- 预期结果
  1. 记录成功。
  2. 改选成功。
  3. 展示时间全部按 Hawaii 口径变化（-18h，跨日），但列表顺序仍为 R1…R5——排序键（首次提交时刻）不变。
  4. 补发后 R3 仍在其原排序位（补发不置顶，US-034 排序键口径）。

## [P2] 验证切换时区前后同一事件服务端时刻不变（守恒量）
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，当前时区 Beijing
  2. 已知某告警服务端存储发生时刻为 2026-09-20 10:00:00（UTC+8 基准）
  3. 抓包工具就绪
- 测试步骤
  1. Beijing 口径下记录该告警展示时间（应为 2026-09-20 10:00）。
  2. 改选 London，重进告警页查看展示时间。
  3. 抓包核对告警接口返回的发生时刻原始值。
- 预期结果
  1. 展示 2026-09-20 10:00。
  2. 展示按 London 相位变化（夏令 +1 → 03:00，冬令 +0 → 02:00，按当日现查），仅标签变化。
  3. 接口返回原始时刻仍为 2026-09-20 10:00:00（+8 基准）——切换时区不改变服务端保存的事件时刻。

## [P5] 验证纯日期字段与时戳字段混合页面的两层正确性
- 测试类型
  - 功能
- 前置条件
  1. 账号 testuser01 已登录，当前时区 Beijing
  2. 设备详情页同时含：创建时间（时戳，2026-09-01 08:00 +8 存储）与服务到期日（纯日期 2027-03-15）
- 测试步骤
  1. Beijing 口径记录两字段展示值。
  2. 改选 Tokyo（+9）后重进详情页。
  3. 核对创建时间按 +9 转换（应为 09-01 09:00）、服务到期日不变。
- 预期结果
  1. 记录成功（创建时间 2026-09-01 08:00、到期日 2027-03-15）。
  2. 改选成功。
  3. 创建时间显示 2026-09-01 09:00（时戳参与换算），到期日仍显示 2027-03-15（纯日期不换算）——同页两类字段各自正确。
