# 用户故事：通知提醒保存与加载异常

> 口径依据：大纲 10.3 / 10.4 / 10.5 章。保存失败 → 开关回弹到保存前状态 + 失败提示，服务端保持原值；不允许 UI 假成功；快速连拨以最后一次成功保存为准；加载失败不得显示假默认值冒充真值、应重试，具体空白 / 重试 UI 待确认 #3（只断言不冒充）。

## [P3][反向] 验证弱网下保存失败开关回弹
- 测试类型
  - 可靠性
- 前置条件
  1. Sound 服务端原值 = 开
  2. 抓包工具可让保存接口超时 / 返回 500
- 测试步骤
  1. 进入通知提醒页确认 Sound 为开。
  2. 模拟保存失败，将 Sound 拨为关。
  3. 等待失败响应，查看开关状态与提示。
  4. 恢复网络重进页面。
- 预期结果
  1. 显示服务端原值开。
  2. 保存请求发出。
  3. 失败后开关回弹为开并提示失败（不允许 UI 已关、服务端仍开的假状态）。
  4. 重进仍为开，服务端原值未变。

## [P3][反向] 验证配置加载失败不显示假默认值冒充真值
- 测试类型
  - 可靠性
- 前置条件
  1. 服务端真实配置 Sound = 关、振动 = 关
  2. 抓包工具可让配置读取接口失败
- 测试步骤
  1. 冷启动后首次进入通知提醒页，模拟读取接口失败。
  2. 查看两开关在加载失败时的展示。
  3. 恢复接口并触发重试。
  4. 查看加载成功后的状态。
- 预期结果
  1. 读取失败。
  2. 不显示默认全开冒充服务端真值；应呈现加载 / 失败 / 重试态（具体 UI 待确认 #3）。
  3. 重试请求成功。
  4. 显示关 / 关，与服务端一致。

## [P3] 验证快速连拨以最后一次成功保存为准
- 测试类型
  - 稳定性
- 前置条件
  1. Sound 初始为开，网络存在延迟但请求可成功
  2. 抓包工具就绪
- 测试步骤
  1. 快速连续拨动 Sound：开 → 关 → 开 → 关。
  2. 等待所有请求完成。
  3. 重进通知提醒页拉取服务端状态。
  4. 核对中间请求是否产生冲突配置。
- 预期结果
  1. 操作过程不崩溃、不出现开关闪乱。
  2. 以最后一次成功保存的「关」为最终服务端值（或客户端串行 / 合并请求保证最后意图）。
  3. 重进显示关。
  4. 不产生多份冲突配置，保存接口幂等。

## [P4] 验证一个开关保存失败不回滚另一个已成功字段
- 测试类型
  - 可靠性
- 前置条件
  1. 初始 Sound = 开、振动 = 开
  2. 可控制：Sound 保存成功、随后振动保存失败
- 测试步骤
  1. 将 Sound 切为关并确认保存成功。
  2. 将振动切为关，但模拟保存失败。
  3. 查看两个开关终态。
  4. 重进页面核对服务端状态。
- 预期结果
  1. Sound 服务端值变为关。
  2. 振动保存失败。
  3. Sound 保持关；振动回弹为开（失败只回滚对应独立字段）。
  4. 重进显示关 / 开，互不覆盖。

## [P3] 验证相同通知配置 PATCH 重放保持幂等且无重复副作用
- 测试类型
  - 可靠性
- 前置条件
  1. 账号 testuser01 服务端配置 Sound = 开、振动 = 开
  2. 接口工具可固定 request-id=nt-20261008-0001 并查询配置版本及审计事件
- 测试步骤
  1. 发送 PATCH 请求将 Sound 改为关，携带 request-id=nt-20261008-0001。
  2. 首次响应成功后，原样重放相同请求、请求体和 request-id。
  3. 查询服务端 Sound 值、配置版本变更次数和审计事件数。
  4. 重进通知提醒页查看两开关状态。
- 预期结果
  1. 首次 PATCH 成功，Sound 变为关，振动保持开。
  2. 重放请求返回与首次一致的幂等结果或明确标识已处理，不重复执行更新。
  3. Sound 最终仅为关，配置版本只增加 1 次、对应审计副作用只产生 1 次，振动字段未被覆盖。
  4. 页面显示关/开，与服务端唯一终态一致。
