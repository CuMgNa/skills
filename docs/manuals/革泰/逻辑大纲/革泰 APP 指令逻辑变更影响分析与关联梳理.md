# 革泰 APP 指令逻辑变更影响分析与关联梳理

> **文档用途**：统一记录革泰 APP 指令下发新口径、APP 与 PN06/808 现有能力差异、单设备/批量/设备详情三个入口的目标流程、关联逻辑大纲影响范围、潜在风险及后续修改清单。
>
> **文档性质**：需求变更影响分析，不代表相关功能已经完成研发改造。涉及 PN06 高危短期队列、过期回调、在线真源、回文关联等内容，必须结合代码与接口实现进一步确认。
>
> **创建日期**：2026-10-08

---

## 1. 背景与核心变化

原《革泰 APP 指令单设备与批量下发逻辑点梳理 plan.md》总体采用以下旧规则：

1. 单设备离线时允许进入指令页，但七类指令最终确认时统一被服务端拦截；
2. 批量选择页中的离线/未连接设备置灰、不可选择；
3. 设备详情页 `Location Interval` 只有设备在线时才能修改并提交 `UPLOAD`；
4. 七类指令统一使用在线状态作为提交条件。

该规则与 PN06/808 的现有技术能力并不一致。PN06 当前支持先保存指令并放入设备待发队列，即使设备当前未连接，也可以等待终端后续心跳、定位、鉴权或补传时再写出。

本轮确认后的目标口径为：

- `CR / VERNO / FIND / UPLOAD / ZONE` 为**普通队列类指令**，不限制设备在线、离线或未连接状态；
- `RESET / POWEROFF` 为**高危短效类指令**，提交时必须由 PN06 活跃通信状态确认在线；
- 高危指令采用“短期车票”机制，不进入普通指令最长 30 天的待发队列；
- 高危指令超过短期有效窗口仍未真正写出时，必须失败、出队，设备后续上线不得补发；
- 设备详情页 `Location Interval / UPLOAD` 与其他 UPLOAD 入口保持一致，离线或未连接时也允许用户主动提交；
- 批量选择阶段允许选择所有设备状态，只有选择高危指令后才处理离线设备限制。

## 2. 当前七类指令与目标分类

### 2.1 页面业务指令

| 页面分类 | 页面指令 | 协议命令 | 参数 | 目标类别 | 设备状态要求 |
| --- | --- | --- | --- | --- | --- |
| 常用指令 | 立即定位 | `CR` | 无 | 普通队列类 | 在线、离线、未连接均可提交 |
| 常用指令 | 查询版本 | `VERNO` | 无 | 普通队列类 | 在线、离线、未连接均可提交 |
| 现场操作 | 查找设备 | `FIND` | 无 | 普通队列类 | 在线、离线、未连接均可提交 |
| 参数设置 | 设置上传间隔 | `UPLOAD` | 上传间隔秒数 | 普通队列类 | 在线、离线、未连接均可提交 |
| 参数设置 | 设置设备时区 | `ZONE` | UTC 偏移 | 普通队列类 | 在线、离线、未连接均可提交 |
| 设备控制 | 远程重启 | `RESET` | 无 | 高危短效类 | 仅 PN06 活跃在线时可提交 |
| 设备控制 | 远程关机 | `POWEROFF` | 无 | 高危短效类 | 仅 PN06 活跃在线时可提交 |

### 2.2 底层协议承载

七个页面业务动作并不是七种独立的 PN06 消息类型。当前 PN06/808 统一按文本指令承载：

- podium 单设备调用：`GET /api/code/text/{addr}?code=...`；
- podium 批量调用：`POST /api/code/batch/text`；
- PN06 下行消息 ID：`0x8300`；
- 设备业务回文同样按 `0x8300` 文本帧接收。

因此，业务层必须显式维护 `commandType` 和安全类别，不能依赖底层消息 ID 区分普通指令与高危指令。

## 3. APP 旧规则、PN06 现状与新需求对比

| 对比项 | APP 旧大纲 | PN06/808 当前能力 | 新需求目标 |
| --- | --- | --- | --- |
| 单设备离线提交 | 可进入页面，但最终统一拒绝 | 可以先入队等待设备通信 | 普通五类允许；高危两类禁止 |
| 批量离线设备 | 置灰、不可选择 | 技术上可以为离线设备创建待发任务 | 所有状态均可选择；选择高危后处理离线设备 |
| 详情页定位频率 | 离线置灰，不创建 UPLOAD | 可以保存 UPLOAD 并等待设备上线 | 离线/未连接也允许主动设置 |
| 指令真正发送时机 | 原大纲未展开 | 心跳/定位/鉴权/补传触发写出 | 普通指令沿用；高危指令使用短期有效机制 |
| 普通指令队列时长 | 因离线被拦截，无离线队列 | 当前最长 30 天 | 暂沿用 PN06 普通队列逻辑 |
| 高危指令队列时长 | 与其他指令无明确差异 | 当前仍属于通用文本队列 | 短期有效，过期失败并出队 |
| “指令已提交”含义 | 至少一台被服务端受理 | 808 收下并入队，设备未必收到 | 仍只表示平台已受理，不表示设备已执行 |
| `SENT` 含义 | 容易被误解为执行成功 | 808 已进行 TCP 写出 | 不等于设备业务执行成功 |

## 4. 统一目标流程

### 4.1 普通队列类指令

```text
用户从任一正式入口选择普通指令
→ APP 校验参数和本地表单
→ 革泰服务端校验登录账号、设备关系、设备唯一标识、PN06 路由标识、型号能力、参数和幂等键
→ 不因设备离线或未连接拒绝
→ podium 创建 SENDING 指令记录
→ podium 调用 PN06/808 HTTP 接口
→ 808 写 Mongo，isSend=false，并按设备 addr 放入待发队列
→ 在线设备等待最近一次心跳/定位/鉴权/补传触发
→ 离线设备继续等待后续通信机会
→ 808 下发 0x8300 文本指令
→ 写出后 isSend=true，从待发队列移除
→ 808 回调 podium，记录更新为 SENT
→ 设备业务回文经独立数据推送链路回写 feedbackText / feedbackTime
```

普通指令进入 `SENDING` 只表示平台或 PN06 已受理，不能解释为设备已收到或已执行。

### 4.2 高危短效类指令

```text
用户选择 RESET / POWEROFF
→ APP 展示高危影响说明并进行二次确认
→ 服务端查询 PN06 活跃通信状态
→ 当前不活跃：拒绝该设备
→ 当前活跃：创建带 expireAt 的高危短效任务
→ 在短期有效窗口内等待或直接写出
→ 窗口内写出：状态进入 SENT
→ 窗口内未写出：状态进入 FAILURE，并从数据库/内存待发队列移除
→ 设备在过期后重新上线：不得再执行旧高危指令
→ 用户仍需操作时必须重新发起并重新校验在线状态
```

高危短期有效窗口的具体时长、起算点和实现方式尚未确认，不能在测试文档中自行写死数值。

## 5. 三个入口的目标逻辑

### 5.1 单设备 Send Command

#### 在线设备

- 允许进入当前设备指令页；
- 七类指令全部展示且可选；
- 普通五类提交后进入普通 PN06 队列；
- RESET/POWEROFF 提交时由服务端按 PN06 活跃通信状态重新校验；
- APP 页面展示的在线状态只是快照，不能替代最终服务端裁决。

#### 离线或未连接设备

- 仍允许从设备卡片更多菜单进入指令页；
- `CR/VERNO/FIND/UPLOAD/ZONE` 正常可选、可设置参数、可提交；
- `RESET/POWEROFF` 置灰；
- 置灰时展示可读原因，例如“设备离线，仅在线设备可远程重启”；
- 服务端必须校验指令类别和 PN06 活跃状态，防止构造请求绕过前端。

### 5.2 批量下发

#### 设备选择阶段

- 在线、离线、未连接和告警设备均可选择；
- “全选当前结果”选择当前状态、分组、关键词交集范围内全部有权限设备；
- 同一设备按设备唯一标识去重；
- 设备选择阶段尚未确定具体指令，不能预先把离线设备排除。

#### 选择普通指令

- 在线、离线、未连接设备均可进入确认；
- 最终校验时，离线不属于普通指令失败原因；
- 权限失效、设备不存在、路由标识缺失、型号不支持、参数非法等仍独立失败；
- 有效设备进入普通 PN06 队列。

#### 选择高危指令

如果当前选择中已经存在离线或未连接设备：

1. 阻止进入最终确认；
2. 展示离线/未连接设备数量，必要时支持查看明细；
3. 引导用户移除这些设备；
4. 不得静默剔除，否则用户可能误以为原选择范围全部执行。

#### 最终确认时部分设备掉线

最终确认必须再次查询 PN06 活跃通信状态：

| 最终结果 | 目标处理 |
| --- | --- |
| 全部设备活跃 | 全部进入高危短效任务 |
| 部分活跃、部分掉线 | 活跃设备继续；掉线设备独立失败；不回滚有效设备 |
| 全部掉线 | 整批不受理，不显示“指令已提交” |
| 至少一台受理 | 可以显示统一提交弹窗，逐设备结果进入本次批次记录 |

批量选中数量应满足：

```text
选中数量 = 已受理数量 + 最终复检失败数量
```

掉线设备是否创建 `FAILURE` 明细尚需正式确认；从数量守恒和审计角度，建议创建失败明细并记录失败阶段。

### 5.3 设备详情 Location Interval

`Location Interval` 最终产生 `UPLOAD`，属于普通队列类指令，必须与 Send Command 和批量下发中的 UPLOAD 保持一致。

目标流程：

```text
进入设备详情
→ 点击 Edit
→ 不区分在线、离线或未连接，均允许打开 Location Interval 弹层
→ 选择预设值或自定义分钟数
→ 弹层 Save 只写入本地表单
→ 点击整页 Save
→ 普通资料接口与 UPLOAD 指令接口分别提交
→ UPLOAD 受理后进入 SENDING
→ 离线设备等待后续通信机会
→ 设备回文被后端可靠关联并判定成功后，才更新最后确认频率
```

必须继续区分：

- 最后确认值；
- 本地编辑目标值；
- 设置中目标；
- SENDING；
- SENT；
- 设备业务反馈成功。

平台受理、进入 SENDING 或 TCP 写出为 SENT，都不能直接证明定位频率已经生效。

## 6. 指令状态语义

| 状态/字段 | 业务含义 | 禁止误解 |
| --- | --- | --- |
| `SENDING` | 平台或 PN06 已受理，可能正在待发队列等待 | 不等于设备已收到 |
| `SENT` | PN06 已经执行 TCP 写出并回调 podium | 不等于设备已执行业务动作 |
| `FAILURE` | 前置校验、调用网关、队列、过期或其他明确失败 | 需要保留具体失败阶段和原因 |
| `CANCEL` | 尚未写出时真正取消成功，具体 PN06 竞态语义待确认 | 不能默认等同于 S10U 乐观取消 |
| `feedbackText` | 设备业务回文内容 | 不一定能证明业务成功，需后端解析 |
| `feedbackTime` | 设备业务回文时间 | 不等同于 TCP 写出时间 |

## 7. 主要遗漏与潜在风险

### 7.1 P0：解绑、失权、改绑后的旧指令

典型风险：

```text
账号 A 对离线设备提交 UPLOAD
→ 指令在 PN06 等待
→ 设备从 A 解绑并改绑给 B
→ 设备上线
→ A 创建的旧指令被执行
```

必须明确：

1. 解绑、企业分配回收、改绑时是否取消所有未写出指令；
2. 真正发送前是否重新校验当前设备关系；
3. 企业一级解绑导致整个下级链路失效时，相关待发指令如何清理；
4. 已 SENT 指令只保留审计，不尝试回滚；
5. 旧账号失权后禁止取消、重发或查看受保护详情。

建议默认规则：关系失效时清理该关系创建的所有未写出任务，发送前再次鉴权，避免旧账号指令延迟执行。

### 7.2 P0：普通队列 30 天丢弃未回写业务状态

PN06 当前说明只证明超过 30 天会从队列丢弃，尚未证明一定通知 podium 更新为 FAILURE。可能出现：

```text
PN06 已删除队列项
podium 仍永久显示 SENDING
```

需要补充：

- 普通过期事件；
- 高危短期过期事件；
- PN06 到 podium 的失败回调；
- 回调失败重试或 outbox；
- 幂等的 SENDING → FAILURE；
- 队列、808 Mongo、podium 记录的最终一致性。

### 7.3 P0：高危短效机制当前并不存在

当前 PN06 是统一文本队列，没有正式的高危类别和独立 TTL。必须新增稳定字段和服务端校验，不能只改 APP 按钮。

### 7.4 P0：高危指令依赖下一次终端上报

PN06 当前在终端心跳、定位、鉴权或补传时冲待发队列，不是 podium 提交后必然立即写出。

需要确认：

- 高危指令是否改为当前 channel 可写时立即发送；
- 若仍等待下一次上报，短期窗口如何覆盖正常心跳周期；
- PN06 活跃状态是否等于 channel 存在且可写；
- 状态查询失败时按系统异常处理，不能伪装为设备离线。

### 7.5 P0：设备回文近似匹配可能更新错指令

当前 PN06 按同一 addr 最新已发送指令近似挂靠回文，不保证严格匹配原命令。开放离线队列后，同一设备积压多条 UPLOAD/ZONE/CR 会放大风险。

至少需要一种治理方式：

1. 协议携带可回传流水号；
2. 按命令类型与参数解析后匹配；
3. 同设备同类配置指令串行化；
4. 无法可靠匹配时只展示回文，不更新最后确认值；
5. 旧回文不得覆盖较新的 UPLOAD/ZONE 目标。

### 7.6 P0：配置指令积压后的覆盖策略未定义

离线期间可能连续提交：

```text
UPLOAD,600
UPLOAD,3600
ZONE,+08
UPLOAD,60
```

需要明确：

- 全部按顺序发送；
- 还是同一配置项只保留最后一条未写出目标；
- 被覆盖任务标记 CANCEL、FAILURE 还是单独的 SUPERSEDED；
- 旧回文晚到后是否允许改变最终确认值。

建议 UPLOAD、ZONE 对未写出任务采用同配置项最后值策略，并保留被覆盖记录用于审计。

### 7.7 P1：CR/FIND 长期排队的业务时效风险

本轮已确认 CR 和 FIND 属普通队列类，允许离线并暂沿用 PN06 普通队列，但需要显式接受：

- “立即定位”可能很久以后才执行；
- “查找设备”可能设备重新上线后突然鸣响；
- 用户可能已经完成现场操作，却忘记队列中仍有任务。

建议页面明确提示“设备上线后执行”，并允许用户在真正写出前取消任务。

### 7.8 P1：未连接不等于具备合法路由

允许未连接设备提交普通指令的前提是设备已经具有合法 PN06 addr/卡号。以下情况不能按普通离线队列成功处理：

- 缺少 addr；
- addr 格式非法；
- 设备未接入 PN06；
- 设备已注销；
- 型号不支持当前指令。

失败提示必须区分路由错误、权限错误、型号不支持和设备离线。

### 7.9 P1：批量高危部分失败记录边界

最终复检掉线的设备建议创建失败明细，并记录：

```text
failureStage = FINAL_RECHECK
failureReason = PN06_NOT_ACTIVE
```

否则批次选中数量与实际记录数量不一致，用户无法确认哪些设备没有执行。

### 7.10 P1：PN06 与 S10U 取消语义不一致

S10U 文档存在乐观取消和 CANCEL 回写 SENT；PN06 当前更接近未发送才能取消。必须确认 PN06 最终采用哪一种，不得继续直接继承 S10U 状态机。

### 7.11 P1：普通和高危重发规则必须分开

| 指令类别 | 重发规则 |
| --- | --- |
| 普通队列类 | 离线也可重发，生成新的用户操作 attempt |
| 高危短效类 | 必须重新查询 PN06 活跃状态，并重新计算 TTL |
| 网络超时重试 | 沿用当前 operationId，不创建新指令 |
| 用户主动重新发送 | 新用户意图，生成新的 operationId / attemptId |

### 7.12 P1：服务到期规则未裁决

需要分别确认查询类、现场类、配置类和高危控制类在以下情况下能否提交或继续执行：

- 提交时已经到期；
- 提交时未到期、排队期间到期；
- 到期后续费恢复；
- 高危短效任务等待期间服务到期。

### 7.13 P1：型号能力矩阵缺失

必须建立：

```text
型号 × 指令 × 参数范围 × 回文格式 × 在线能力 × 队列能力
```

批量混合型号时，服务端必须逐台判断能力，不得只靠 APP 假定所有设备支持七类指令。

## 14. 验收红线

1. 普通五类不得因为设备离线或未连接被统一拒绝；
2. RESET/POWEROFF 不得进入普通 30 天队列；
3. 高危短期窗口过期后，设备上线不得执行旧指令；
4. APP 在线快照不得替代 PN06 活跃通信状态；
5. 缺少 PN06 路由标识不得伪装成正常离线排队；
6. 解绑、失权或改绑后，旧账号未写出指令不得延迟控制设备；
7. 普通和高危过期时，队列清理与业务 FAILURE 状态必须最终一致；
8. SENT 只能表示 PN06 已执行 TCP 写出，不得表示设备业务执行成功；
9. UPLOAD/ZONE 的旧回文不得覆盖更新目标；
10. 批量部分成功必须满足数量守恒并能逐设备追溯；
11. 用户主动重发与网络重试必须使用不同的 attempt/幂等语义；
12. 页面不得继续使用“离线，无法下发指令”表达全部指令能力。
