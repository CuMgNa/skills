# 革泰 APP 取消回写已发送逻辑修改清单

> 文档状态：待评审
>
> 适用范围：普通指令与高危指令的取消、状态回写、记录展示、批量统计、配置值联动，以及四份关联文档的明确矛盾和用户体验统一要求
>
> 核心约束：现阶段保留“APP 先乐观显示已取消，网关确认实际已写出后允许回写为已发送”的现有机制
>
> 关联文档：
>
> 1. 《革泰 APP 设备管理逻辑点梳理 plan》
> 2. 《革泰 APP 指令单设备与批量下发逻辑点梳理 plan-v2草案》
> 3. 《革泰 APP 指令记录逻辑点梳理 plan》
> 4. 《S10U 指令交互状态逻辑点梳理》

---

## 1. 修改目的

当前取消链路采用乐观交互：用户点击取消后，APP 先将记录展示为 `CANCEL / 已取消`；如果后续网关确认任务在取消生效前已经完成 TCP 写出，则再将状态从 `CANCEL` 修正为 `SENT / 已发送`。

本次不改变上述核心机制，但需要解决以下问题：

1. `CANCEL` 在不同文档中被同时描述为终态、临时态和可反转状态；
2. APP 展示“已取消”后，设备仍可能执行指令，尤其会影响远程重启和远程关机；
3. 当前规则规定 `CANCEL → SENT` 时不提示用户，存在明显误导；
4. 批量 L1、L2 统计和筛选没有完整定义状态反转后的同步规则；
5. 定位频率等配置类指令在 `CANCEL → SENT` 时存在目标值先回退、再恢复的问题；
6. 当前记录没有保留取消请求时间、取消最终结果及状态修正轨迹；
7. 重复回调、乱序回调可能造成 `SENT` 被旧取消结果覆盖；
8. APP 切后台、退出或离线期间发生状态反转时，用户可能永久错过提醒。

本次修改的目标是：

> 在保留乐观取消体验的前提下，把 `CANCEL → SENT` 从隐含的技术竞态补充为完整、可解释、可审计、可测试的产品规则。

---

## 2. 统一结论

### 2.1 核心状态规则

统一采用以下规则：

```text
1. 只有 SENDING 状态允许发起取消。

2. 用户点击取消后：
   - APP 可以立即乐观展示 CANCEL；
   - 此时的 CANCEL 代表取消请求已被 APP 接受并进入处理；
   - 不代表平台已绝对确认指令不会写出。

3. 网关确认任务未写出且队列删除成功：
   - CANCEL 最终生效；
   - 任务不再写出；
   - 不再等待设备反馈。

4. 取消处理期间发现任务已经完成 TCP 写出：
   - 已发生的写出事实优先；
   - 状态允许从 CANCEL 修正为 SENT；
   - 后续设备反馈继续关联原 attempt；
   - APP 必须提示用户取消未阻止本次下发。

5. SENT 不允许再回到 CANCEL。

6. SENT 仅代表完成 TCP 写出：
   - 不代表设备一定收到；
   - 不代表设备一定执行；
   - 不代表设备执行成功。
```

### 2.2 状态机

普通指令与高危指令均保留以下状态跃迁：

```text
SENDING → SENT
SENDING → FAILURE
SENDING → CANCEL
CANCEL  → SENT
```

禁止出现：

```text
SENT → CANCEL
FAILURE → CANCEL
CANCEL → FAILURE（除非后续另行新增明确业务规则）
```

### 2.3 状态优先级

统一事实优先级：

```text
可靠的 TCP 写出成功事实
>
APP 乐观取消展示
```

即一旦网关能够可靠证明 TCP 已完成写出，最终发送状态必须收敛为 `SENT`。

### 2.4 CANCEL 的统一定义

建议在所有关联文档中统一使用以下定义：

> `CANCEL`：用户已发起取消，APP 已乐观展示“已取消”。正常情况下表示任务在写出前被删除；但如果后续确认指令在取消生效前已经完成 TCP 写出，状态允许被修正为 `SENT`。因此，`CANCEL` 是当前用户可见状态，但不是绝对不可变的技术终态。

## 3. 取消与写出的竞态决策表

| 场景 | 页面初始表现 | 最终发送状态 | TCP 写出 | 设备是否可能执行 | 用户提示 |
|---|---|---|---|---|---|
| 网关尚未写出，删除队列成功 | 已取消 | CANCEL | 否 | 否 | 取消成功 |
| TCP 已写出后才收到取消请求 | 可先显示已取消 | SENT | 是 | 是 | 取消未生效，指令已下发 |
| 删除队列和 TCP 写出并发，删除获胜 | 已取消 | CANCEL | 否 | 否 | 取消成功 |
| 删除队列和 TCP 写出并发，写出获胜 | 先显示已取消 | CANCEL → SENT | 是 | 是 | 取消未生效，指令已下发 |
| APP 已显示 CANCEL，迟到写出回调到达 | 已取消 | CANCEL → SENT | 是 | 是 | 必须提示状态已修正 |
| SENT 后迟到取消结果到达 | 已发送 | SENT | 是 | 是 | 不回退为已取消 |
| 重复写出回调 | 已发送 | SENT | 已发生一次 | 不重复产生执行 | 不重复提示、不重复统计 |
| 重复取消请求 | 已取消或已发送 | 保持当前权威状态 | 以首次处理结果为准 | 以权威状态为准 | 返回当前最新结果 |

## 4. 《S10U 指令交互状态逻辑点梳理》修改清单

### 4.1 修改状态定义表

原有 `CANCEL` 定义应补充为：

| 状态 | 中文展示 | 进入条件 | 是否终态 |
|---|---|---|---|
| SENDING | 发送中 / 等待发送 | 服务端校验通过并创建待写出任务 | 否 |
| SENT | 已发送 / 已下发 | S10U 已完成 TCP 写出并回调 | 是，发送状态层面不可回退为 CANCEL |
| FAILURE | 发送失败 | 权限、关系、路由、能力、参数、环境、会话或队列过期等明确失败 | 是 |
| CANCEL | 已取消 | APP 已乐观展示取消；正常情况下任务未写出且队列删除成功 | 否，仍允许被迟到的可靠写出事实修正为 SENT |

### 4.2 修改普通指令生命周期说明

补充：

```text
SENDING → CANCEL：APP 发起取消并乐观展示已取消。

CANCEL 保持不变：网关确认任务未写出且队列删除成功。

CANCEL → SENT：取消处理期间发现任务已经完成 TCP 写出，
已发生的写出事实优先，状态修正为 SENT。
```

### 4.3 修改高危指令生命周期说明

补充：

1. `RESET / POWEROFF` 允许采用与普通指令相同的乐观取消状态；
2. `CANCEL → SENT` 后，设备仍可能执行重启或关机；
3. 状态修正后必须产生高优先级用户提醒；
4. 状态修正不代表设备一定执行成功，仍应以后续设备反馈为准；
5. 高危指令不得因为取消失败而再次自动写出；只能承认已经发生的原始写出事实。

### 4.4 新增写出与取消原子竞态规则

建议新增以下规则：

```text
1. 同一 attempt 的写出和取消必须以唯一状态版本收敛。
2. 写出成功事件一旦被可靠确认，不允许被迟到取消事件覆盖。
3. 删除队列成功且确认未写出后，迟到的普通任务调度不得再次写出。
4. CANCEL → SENT 只能发生一次。
5. 重复 SENT、重复取消结果、重复反馈均不得重复产生业务副作用。
6. 旧 attempt 的事件不得覆盖当前 attempt 的用户可见投影。
```

### 4.5 新增内部取消解析状态

APP 对外仍维持四态，但服务端内部建议增加：

```text
cancelResolution:
- PENDING               取消请求处理中或尚未完成权威确认
- CONFIRMED             已确认未写出且队列删除成功
- OVERRIDDEN_BY_SENT    已确认取消未阻止写出，状态已修正为 SENT
```

说明：

- `cancelResolution` 不是 APP 第五种发送状态；
- 它用于配置值联动、审计、消息通知、状态修正和测试断言；
- APP 是否直接展示该字段可另行决定。

### 4.6 新增事件版本与幂等要求

建议状态事件至少包含：

```text
eventId
attemptId
businessId
stateVersion
occurredAt
eventType
```

处理规则：

1. 相同 `eventId` 只处理一次；
2. `stateVersion` 只能递增；
3. 旧版本事件不得覆盖新版本状态；
4. `SENT` 后到达的旧取消结果只能补充审计，不能修改发送状态；
5. 重复事件不得重复更新批次数量或重复发送用户提醒。

## 5. 《革泰 APP 指令记录逻辑点梳理 plan》修改清单

### 5.1 修改“取消发送”规则

原规则中“CANCEL 回写 SENT 时无失败弹窗”需要修改。

建议统一为：

```text
1. 用户点击取消后，卡片可以先乐观更新为“已取消”。
2. 网关确认任务未写出且删除成功后，维持“已取消”。
3. 如果后续确认任务实际已完成 TCP 写出，卡片从“已取消”修正为“已发送/已下发”。
4. 状态修正后必须提示用户“取消未生效，指令已下发”。
5. RESET / POWEROFF 状态修正时必须使用高优先级提醒。
6. 状态修正不新增用户可见卡片，仍更新原 commandId 对应卡片。
```

### 5.2 修改“取消动作不留时间痕”规则

当前“取消动作不留时间痕”应删除，改为后台保留完整审计字段：

```text
cancelRequestedAt
cancelDisplayedAt
cancelResolvedAt
cancelOutcome
statusCorrectedAt
sentAt
```

页面主卡可以不全部展示，但记录详情、管理端或问题排查接口必须能够查询。

### 5.3 新增状态修正轨迹

建议记录详情提供事件时间线：

```text
14:02:01 用户发起取消
14:02:01 APP 乐观显示已取消
14:02:02 网关确认指令已完成 TCP 写出
14:02:02 状态修正为已下发
```

主卡仍只展示最新状态，避免信息过载；但不能只覆盖结果而完全丢失取消过程。

### 5.4 修改批量 L1/L2 统计规则

明确批量统计允许发生以下变化：

```text
CANCEL → SENT 时：
取消数 -1
已发送数 +1
```

必须始终满足：

```text
批次设备明细总数
= SENDING + SENT + FAILURE + CANCEL
```

同步要求：

1. L2 卡片先更新为最新状态；
2. L1 汇总最终同步；
3. 当前筛选为“已取消”时，该卡片应从结果中移出；
4. 当前筛选为“已发送”时，该卡片应进入结果；
5. 排序位置按最新状态重新计算；
6. 重复状态回调不得重复增减统计；
7. L1 与 L2 短暂不一致可以接受，但需要明确最终一致时限和最后更新时间。

### 5.5 修改刷新规则

当前仅“手动下拉刷新 + 操作后局部更新”不足以覆盖迟到状态修正。

建议新增：

1. 页面从后台恢复前台时刷新；
2. 页面可见期间允许低频轮询或接收状态推送；
3. 展示“最后更新于 HH:mm:ss”；
4. 刷新失败时保留旧数据，但提示“状态更新失败”；
5. 高危 `CANCEL → SENT` 即使页面不在前台，也应生成消息中心记录或系统通知。

### 5.6 修改状态修正后的用户提示

普通指令推荐文案：

> 取消未生效，指令已下发。设备是否执行请以后续反馈为准。

远程重启推荐文案：

> 远程重启取消未生效，指令已下发至设备，设备仍可能执行重启。

远程关机推荐文案：

> 远程关机取消未生效，指令已下发至设备，设备仍可能执行关机。

### 5.7 修改字段展示说明

`SENT` 的中文建议统一为“已下发”，或者在“已发送”旁固定解释：

> 仅表示平台已完成指令下发，不代表设备已执行。

取消修正为 SENT 后：

- 发送时间展示真实 `sentAt`；
- 反馈内容继续按后续设备回复展示；
- 不展示“取消发送”按钮；
- 不自动提供重发按钮；
- 取消请求轨迹保留在详情中。

## 6. 《革泰 APP 指令单设备与批量下发逻辑点梳理 plan-v2草案》修改清单

### 6.1 修改高危会话生命周期

当前 `SENDING_BOUND` 建议不要作为 APP 第五态。

统一表示为：

```text
status = SENDING
boundSessionId = 当前绑定会话
sessionEpoch = 当前会话纪元
```

高危生命周期修改为：

```text
SENDING + boundSession
├─ 同一绑定会话内写出成功 → SENT
├─ 绑定会话断开 → FAILURE + 出队
├─ 当前会话被新会话替换 → FAILURE + 出队
├─ 设备关系失效 → FAILURE + 出队
├─ 用户发起取消 → APP 乐观展示 CANCEL
│  ├─ 未写出且队列删除成功 → 维持 CANCEL
│  └─ 已实际完成写出 → CANCEL 修正为 SENT
└─ 最大有效时间到期 → FAILURE + 出队
```

### 6.2 修改写出与取消竞态表

建议将原“同一任务只有一个最终结果”调整为：

> 同一任务的权威发送结果必须最终收敛，允许 APP 乐观 CANCEL 被已发生的 SENT 事实修正，但不允许 SENT 再被取消结果覆盖。

决策表：

| 原子事实先完成 | 权威结果 |
|---|---|
| TCP 写出成功 | SENT |
| 未写出且用户取消删除队列成功 | CANCEL |
| 断线清队列成功 | FAILURE |
| 关系失效清理成功 | FAILURE |
| APP 先展示 CANCEL，后确认已写出 | CANCEL → SENT |
| SENT 后迟到取消结果 | 保持 SENT |

### 6.3 修改取消接口语义

建议取消接口返回当前用户可见状态和内部取消解析状态：

```json
{
  "commandId": "...",
  "attemptId": "...",
  "status": "CANCEL",
  "cancelResolution": "PENDING",
  "stateVersion": 12
}
```

后续可能收敛为：

```json
{
  "status": "CANCEL",
  "cancelResolution": "CONFIRMED",
  "stateVersion": 13
}
```

或：

```json
{
  "status": "SENT",
  "cancelResolution": "OVERRIDDEN_BY_SENT",
  "stateVersion": 14
}
```

### 6.4 新增重复取消的幂等规则

1. 同一 attempt 的重复取消请求复用同一取消操作；
2. 不重复删除队列；
3. 不重复发送状态修正通知；
4. 已 SENT 的任务返回最新 SENT，不允许改回 CANCEL；
5. 请求超时后重试应使用原取消幂等键；
6. APP 不得因为取消接口超时而自动创建新的指令 attempt。

### 6.5 修改高危确认弹窗

在 RESET / POWEROFF 二次确认中补充：

> 指令发送与取消可能并发。若指令已开始下发，取消操作可能无法阻止设备执行。

远程关机确认文案示例：

```text
确认远程关机？

关机后设备将离线，可能无法继续定位、上报或接收指令。
指令开始下发后，取消操作可能无法阻止设备执行。

[暂不关机] [确认关机]
```

批量高危确认还需展示：

- 目标设备总数；
- 当前在线设备数；
- 当前无可写会话设备数；
- 告警设备数；
- 状态快照时间；
- “最终结果以服务端逐台复检为准”。

### 6.6 新增批量取消逐设备处理规则

批量取消时，每台设备独立裁决：

| 设备 | 处理结果 |
|---|---|
| A | 未写出且删除成功 → CANCEL |
| B | 已经写出 → SENT |
| C | APP 已展示 CANCEL，稍后确认写出 → CANCEL → SENT |
| D | 已经 FAILURE → 保持 FAILURE |

批量操作不得只返回一个整批“取消成功”而隐藏逐设备实际结果。

## 7. 《革泰 APP 设备管理逻辑点梳理 plan》修改清单

### 7.1 修改 desiredValue 定义

原定义中“未进入 FAILURE / CANCEL 终态”需要调整，因为 CANCEL 不是绝对终态。

建议改为：

> `desiredValue`：最新一条已受理、尚未确认成功，且未进入 `FAILURE` 或未被确认最终取消的目标值。APP 乐观展示 CANCEL、但 `cancelResolution` 仍为 PENDING 时，服务端不得立即销毁该任务的目标参数和关联上下文。

### 7.2 修改配置目标回退规则

统一规则：

| 指令状态 | cancelResolution | 定位频率处理 |
|---|---|---|
| SENDING | 无 | 保留 desiredValue，显示“设置中” |
| SENT，无成功反馈 | 无或 OVERRIDDEN_BY_SENT | 保留 desiredValue，显示“设置中” |
| CANCEL | PENDING | 可按现有交互暂时显示取消，但后台保留目标上下文 |
| CANCEL | CONFIRMED | 从有效目标集合移除，回退到剩余目标或 confirmedValue |
| SENT | OVERRIDDEN_BY_SENT | 恢复或继续保留目标值，显示“设置中” |
| FAILURE | 无 | 从有效目标集合移除，回退到剩余目标或 confirmedValue |
| SENT + 匹配成功 ACK | 无或 OVERRIDDEN_BY_SENT | 更新 confirmedValue |

### 7.3 明确乐观回退的可逆性

如果产品坚持 APP 一展示 CANCEL 就立即回退页面值，则必须补充：

1. 页面回退仅是乐观展示；
2. 服务端仍保留原 `desiredValue`、参数和 `configSequence`；
3. CANCEL 后回写 SENT 时，APP 可以重新恢复目标值并显示“设置中”；
4. 该恢复不是创建新任务，不新增 commandId 或 attemptId；
5. 恢复后继续等待原 attempt 的设备反馈。

### 7.4 明确成功反馈处理

场景：

```text
UPLOAD=600
→ APP 乐观展示 CANCEL
→ 网关回写 SENT
→ 设备返回匹配成功 ACK
```

最终应处理为：

```text
sendStatus = SENT
confirmedValue = 600
```

前提：反馈必须通过以下链路可靠关联：

```text
businessId
→ attemptId
→ commandId
→ configSequence / configIntentVersion
```

旧 attempt 的迟到反馈不得覆盖更新目标。

### 7.5 修改指令四态联动表

建议调整为：

| 指令事件 | 编辑页展示 |
|---|---|
| APP 本地格式校验未通过、请求未发出 | 不创建记录；保持当前有效目标，无目标时回退确认值或“请选择定位频率” |
| 请求已到达服务端，但权限、关系、路由、型号、参数或容量校验失败 | 创建 FAILURE 记录；保持当前有效目标，无目标时回退确认值或“请选择定位频率” |
| SENDING / SENT，尚未确认成功 | 最新有效 desiredValue +“设置中” |
| FAILURE | 回退到最新剩余有效目标；没有则回退 confirmedValue |
| CANCEL + PENDING | 可暂时显示取消后的页面结果，但后台保留目标上下文 |
| CANCEL + CONFIRMED | 回退到最新剩余有效目标；没有则回退 confirmedValue |
| CANCEL 回写 SENT | 恢复或继续视为在途目标，显示“设置中” |
| 后端判定反馈成功 | 更新 confirmedValue；如仍有更新目标，继续显示最新目标“设置中” |

远程关机：

> 确认取消远程关机？如果指令已经开始下发，取消操作可能无法阻止设备执行关机。

### 9.2 乐观取消成功

如果必须保留“取消成功”文案，建议至少增加说明：

> 已提交取消。若指令已经开始下发，状态可能被修正为已下发。

如果允许调整主文案，推荐：

> 取消请求已提交。

### 9.3 状态修正

普通指令：

远程重启：

> 远程重启取消未生效，指令已下发至设备，设备仍可能执行重启。

远程关机：

> 远程关机取消未生效，指令已下发至设备，设备仍可能执行关机。

### 9.4 SENT 状态解释

> 已下发：平台已完成指令发送，不代表设备已执行。

## 10. 保留现有逻辑后的影响说明

### 10.1 用户认知影响

“已取消”不再是绝对不会执行的承诺，而是当前乐观展示结果。若后续确认指令已经写出，状态会修正为已下发。

如果没有明确说明，用户会认为：

- 系统取消逻辑失效；
- 设备无故执行；
- 记录状态自行变化；
- APP 的“取消成功”不可信。

### 10.2 高危指令影响

对于 RESET / POWEROFF：

- 状态修正为 SENT 后，设备仍可能执行重启或关机；
- 设备执行后可能立即离线，导致后续反馈无法返回；
- 没有反馈不代表设备没有执行；
- 必须将状态修正作为高优先级事件通知用户。

### 10.3 批量统计影响

批量统计不是提交后固定不变的结果，可能发生：

```text
已取消 5 台，已发送 10 台
→
已取消 4 台，已发送 11 台
```

因此：

- L1 汇总必须允许反向调整；
- L2 卡片会在不同状态筛选之间移动；
- 统计缓存需要基于状态版本更新；
- 重复回调不得重复增减数量。

### 10.4 配置类指令影响

UPLOAD / ZONE 等配置类指令可能出现：

```text
设置中
→ APP 显示已取消并回退
→ 状态修正为已下发
→ 再次显示设置中
→ 收到设备成功反馈后更新确认值
```

因此不能在第一次显示 CANCEL 时永久删除目标值和任务上下文。

### 10.5 客服与审计影响

需要能够回答：

1. 用户何时发起取消；
2. APP 何时展示已取消；
3. 指令何时实际完成写出；
4. 为什么取消没有阻止写出；
5. 是否发生重复写出；
6. 设备是否返回反馈；
7. 状态修正是否已经通知用户。

只保存最终 SENT 无法支持上述排查。

### 10.6 APP 生命周期影响

如果 CANCEL → SENT 发生时 APP：

- 在后台；
- 被系统杀死；
- 网络断开；
- 用户已退出记录页；

则不能只依赖瞬时 Toast。下次启动或恢复前台时，应展示未读提醒或在消息中心保留记录。

### 10.7 自动化测试影响

自动化不能再把页面第一次出现 CANCEL 当成不可变最终结果。

测试应等待以下任一条件：

- `cancelResolution = CONFIRMED`；
- 状态修正为 SENT；
- 达到明确的最终确认条件。

否则会出现竞态型偶现失败。

### 10.8 下游系统影响

以下下游逻辑不能仅凭首次 CANCEL 永久清理数据：

- desiredValue；
- 配置参数；
- configSequence；
- 设备反馈关联；
- 批量统计；
- 用户通知；
- 操作审计。

## 14. 可直接写入需求文档的统一说明

> 指令取消与设备指令写出可能并发。当用户发起取消时，APP 可先展示“已取消”。如果后续确认该指令在取消生效前已经完成 TCP 写出，系统将把指令状态从“已取消”修正为“已下发”。状态修正后，设备仍可能执行该指令。系统应在指令记录中保留取消请求和状态修正轨迹，并向用户提示取消未阻止本次下发。
>
> “已下发”仅表示平台已完成 TCP 写出，不代表设备已收到、已执行或执行成功。设备最终处理情况以设备反馈为准；没有反馈也不能证明设备未执行。
>
> 对于远程重启和远程关机，若取消状态后续被修正为已下发，设备仍可能执行重启或关机，系统必须进行显著提醒。

## 15. 修改完成后的验收结论标准

只有同时满足以下条件，取消链路才可判定完成闭环：

1. 四份文档对 CANCEL 的定义完全一致；
2. APP、业务服务和 S10U 对状态跃迁的实现一致；
3. CANCEL → SENT 后用户能够感知；
4. 高危指令不会静默从已取消变成已发送；
5. 批量统计最终数量守恒；
6. 配置目标不会因乐观取消被永久错误清除；
7. 旧事件和重复事件不能覆盖、重复统计或重复通知；
8. APP 后台、重启和弱网场景能够恢复最新状态；
9. 后台能够完整追溯取消请求、TCP 写出和状态修正时间；
10. 核心竞态场景已有自动化或可重复的故障注入测试覆盖。

## 16. 明确的跨文档矛盾汇总

本章节汇总四份关联文档中已经能够明确判定的规则冲突。以下问题不能继续由研发自行选择实现口径，需要在需求评审时形成唯一结论，并同步回写所有关联文档。

### 16.1 前置校验失败是否创建 FAILURE 记录

**冲突口径**：

- 设备管理文档的定位频率规则中，前置校验未通过时描述为“未创建记录”；
- 指令下发和 S10U 状态文档要求权限、关系、路由、型号、参数、会话等校验失败进入 `FAILURE`；
- 指令记录文档又要求展示权限、路由、型号等失败原因。

**风险**：

同样是“缺少 S10U 路由”，从设备详情修改定位频率时可能只有 Toast、没有记录；从 Send Command 或批量入口提交时却产生失败记录，导致审计、重发和测试断言不一致。

**统一规则**：

| 失败阶段 | 是否创建记录 |
|---|---|
| APP 本地格式校验未通过，请求未发出 | 不创建后台记录 |
| 请求已到达服务端，能够识别账号、设备和操作意图 | 创建记录 |
| 服务端权限、关系、路由、型号、能力、参数或容量校验失败 | 创建 FAILURE 记录 |
| 批量最终目标范围内的设备校验失败 | 必须创建逐设备 FAILURE 明细 |

建议失败记录增加：

```text
failureStage
failureReasonCode
failureDisplayMessage
failedAt
```

### 16.2 CANCEL 同时被定义为终态和可反转状态

**冲突口径**：

- 设备管理文档曾将 `FAILURE / CANCEL` 一并描述为终态；
- 指令记录及 S10U 状态文档允许 `CANCEL → SENT`；
- 配置值又需要在真正取消后回退，在回写 SENT 后恢复为“设置中”。

**风险**：

研发可能在进入 CANCEL 时永久删除任务上下文，而另一服务随后又尝试回写 SENT，导致配置目标无法恢复、反馈无法关联或状态修正失败。

**统一规则**：

- `FAILURE` 是不可逆发送终态；
- `CANCEL` 是当前用户可见状态，但允许被可靠的 TCP 写出事实修正为 SENT；
- 配置任务只有在 `cancelResolution=CONFIRMED` 后才从有效目标集合移除；
- `SENT` 不允许被迟到取消结果覆盖。

### 16.3 同一高危指令在单设备和批量入口准入不一致

**冲突口径**：

- 单设备页面进入时离线，高危按钮置灰；停留期间恢复在线仍要求退出后重新进入；
- 批量入口允许选择离线设备，最终提交时按实时 S10U 会话逐台复检；
- 批量入口即使只选择一台设备，也继续按批量规则处理。

**风险**：

同一设备、同一时刻、同一 RESET 或 POWEROFF，仅因入口不同，一个页面禁止提交，另一个页面可以成功提交。

**统一规则**：

1. 页面状态只能作为风险提示，不能作为最终安全判断；
2. 单设备和批量高危指令都以提交时服务端实时会话复检为最终准入依据；
3. 单设备页从后台恢复、收到设备在线事件或用户点击高危项时，应刷新当前会话状态；
4. 如果产品坚持单设备入口静态置灰，必须明确记录该入口差异的业务依据，不得继续宣称入口准入一致。

### 16.4 高危重发复检失败时是否创建新 attempt

**冲突口径**：

- 重发总规则规定用户每次主动重发都创建新的 `attemptId`，并累计重发次数；
- 高危重发当前会话复检失败时，又规定只显示 Toast、原失败卡保持不变。

**风险**：

无法判断复检失败是否算一次重发；后台可能已经创建 attempt，但 APP 完全不可见，或 APP 重发次数不增加而审计记录增加。

**统一规则**：

推荐采用：

> 用户完成二次确认即创建新的 attempt。高危会话复检失败时，新 attempt 直接进入 FAILURE，重发次数增加，主卡展示最新失败原因。

如选择“复检通过后才创建 attempt”，则复检失败不能计入重发次数，且所有文档均需采用该规则。两种方案不得混用。

### 16.5 FAILURE 的发送时间展示不一致

**冲突口径**：

- 批量 L2 字段矩阵规定 FAILURE 的发送时间为占位符；
- 单设备失败卡示例存在具体发送时间；
- S10U 状态定义又规定完成 TCP 写出后应进入 SENT。

**风险**：

相同失败在不同入口可能分别展示“已发出”和“未发出”；用户无法判断失败发生在写出前还是写出后。

**统一规则**：

- `sentAt` 只表示成功完成 TCP 写出的时间；
- 只有 SENT 状态展示 `sentAt`；
- FAILURE 展示独立的 `failedAt`；
- 如果未来需要表达设备返回业务失败，应保持发送状态 SENT，并通过独立的设备业务结果字段表达，不能改为发送 FAILURE。

### 16.6 四态模型与 SENDING_BOUND 不一致

**冲突口径**：

- S10U 状态文档明确 APP 发送状态只有 `SENDING / SENT / FAILURE / CANCEL`；
- 指令下发文档的高危生命周期中又出现 `SENDING_BOUND`。

**风险**：

研发可能把 `SENDING_BOUND` 实现为第五种状态，造成 APP 无文案、批量四态统计不守恒、筛选无法定义及接口契约不一致。

**统一规则**：

不新增第五态，统一表示为：

```text
status = SENDING
boundSessionId = 当前绑定会话
sessionEpoch = 当前会话纪元
```

会话绑定属于 SENDING 的业务属性，不属于独立的用户可见状态。

### 16.7 二、三级账号接收设备分配的配额规则不一致

**冲突口径**：

- 一处描述二、三级接收分配是否消耗配额尚待确认；
- 另一处又直接规定账号设备配额已满时，绑定或被分配设备都要拦截。

**风险**：

一级向二级分配设备时，研发无法判断应检查直接绑定配额、分配配额、最终可见设备上限，还是共用一个设备数量上限。

**统一规则**：

至少拆分：

```text
bindingQuota       个人、企业一级直接绑定配额
allocationQuota    企业二级、三级接收设备分配配额
visibleDeviceLimit 当前账号最终可见设备上限
```

需要明确：

1. 各账号层级分别使用哪一类配额；
2. 级联分配是否重复占用配额；
3. 上级回收后如何释放配额；
4. 并发分配时如何防止超额；
5. 配额校验和分配关系创建是否位于同一事务。

### 16.8 “未连接”和“离线”的页面口径存在歧义

**当前口径**：

- 设备管理列表将未连接统一归入离线筛选和统计；
- 指令页面和批量选择又多次将未连接作为独立状态描述。

**风险**：

用户可能在列表看到“离线”，进入指令页后突然看到“未连接”；研发也可能误加独立计数或筛选项。

**统一规则**：

- 后端可以保留 `NEVER_CONNECTED / UNCONNECTED` 原始事实；
- 列表筛选和统计统一归入离线；
- 页面如需区分，展示为“离线·尚未连接”或“离线（暂无通信记录）”；
- 未连接只影响解释文案，不单独改变普通指令和高危指令的最终服务端准入规则。

### 16.9 跨文档矛盾关闭标准

每一项矛盾只有同时满足以下条件才算关闭：

1. 产品形成唯一规则；
2. 四份关联文档同步采用同一术语；
3. 接口字段和状态枚举同步更新；
4. APP 展示与服务端状态机一致；
5. 单设备、批量、记录页重发等入口采用同一校验原则；
6. 正向、反向、并发和弱网场景均有验收用例；
7. 不再保留“研发实现时确认”“后续再定”等影响主流程的悬空描述。

## 17. 第三批：用户体验问题及修改要求

本章节聚焦不会直接改变底层状态机、但会造成用户误解、误操作、重复操作或无法追溯的问题。以下内容建议在状态及逻辑规则完成后作为第三批统一修改。

### 17.1 SENT 容易被误解为设备执行成功

**问题**：

`SENT / 已发送` 只代表 S10U 完成 TCP 写出，但普通用户容易将其理解为设备已收到或已经执行成功，批量“已发送 N 台”尤其容易被理解为成功数。

**修改要求**：

1. 字段名称建议使用“下发状态”；
2. SENT 中文建议改为“已下发”；
3. 固定补充说明“仅表示平台已发出，不代表设备已执行”；
4. 设备反馈单独展示为等待反馈、已收到反馈、执行失败、无需反馈或反馈无法关联；
5. 批量汇总禁止使用“成功 N 台”代替“已下发 N 台”。

### 17.2 SENDING 长时间展示“发送中”容易被认为卡死

**问题**：

普通离线任务可能等待数天甚至接近有效期，持续显示“发送中”无法区分等待设备上线、队列等待、正在写出还是系统卡住。

**修改要求**：

后端继续保持统一 SENDING，APP 根据原因派生展示：

| 场景 | 建议文案 |
|---|---|
| 设备离线 | 等待设备连接后发送 |
| 已进入队列 | 排队等待发送 |
| 网关正在处理 | 正在下发 |
| SENT 但无设备回复 | 已下发，等待设备反馈 |
| 等待时间过长 | 等待时间较长，可查看任务详情 |

同时展示最后状态更新时间、等待时长和任务失效时间。

### 17.3 弱网提交结果未知后容易重复下发

**问题**：

服务端可能已经受理，但 APP 响应超时。若页面立即恢复普通可操作状态，用户再次点击会产生重复 RESET、POWEROFF 或配置任务。

**修改要求**：

1. 请求发出前持久化 `operationId / requestId / batchId`；
2. 超时后进入“正在确认提交结果”，不能直接显示提交失败；
3. 确认期间禁用再次发送，按钮改为“查询提交结果”；
4. 使用原幂等键查询原操作；
5. 只有服务端明确确认原请求未受理，才允许创建新的发送意图；
6. APP 重启、切后台或切换网络后继续恢复原核验流程。

### 17.4 批量结果“查看详情”没有定位本次批次

**问题**：

用户点击部分失败或全部失败弹窗中的“查看详情”后，只进入全量 L1，不携带 `batchId`、不定位、不高亮，连续提交时容易查看错误批次。

**修改要求**：

优先方案：

```text
结果弹窗 → 携带 batchId → 直接进入对应批次 L2
```

次选方案：

- 进入 L1 后滚动定位并高亮本批次；
- 展示短批次号和“本次下发”标识；
- 记录尚未生成时仅轮询当前 batchId；
- 如果完全不定位，按钮文案改为“前往指令记录”，不得继续承诺“查看本次详情”。

### 17.5 批量失败原因缺少分类和下一步建议

**问题**：

同一批次可能同时存在无会话、权限失效、型号不支持、路由缺失、系统异常和服务过期。只展示一个失败总数，用户无法判断哪些可以重试。

**修改要求**：

结果弹窗按用户可理解的原因分组，例如：

```text
设备离线或无可用连接：4 台，可稍后重试
权限已失效：2 台，请联系管理员
设备暂不支持该指令：3 台，不建议重试
系统暂时异常：1 台，可稍后重试
```

原始错误码放入技术详情，普通用户只展示稳定文案和下一步动作。

### 17.6 “重发全部失败”与当前筛选范围容易混淆

**问题**：

页面筛选后只展示部分设备，但固定按钮“重发全部失败（N）”可能作用于整个批次，包括屏幕外和分页外设备；对于重启和关机尤其危险。

**修改要求**：

1. 按钮改为“重发本批次全部失败设备（N）”；
2. 确认框明确“当前筛选仅影响展示，本操作将作用于整个批次”；
3. 如果支持仅重发筛选结果，应使用独立按钮；
4. 二次确认时冻结目标设备快照；
5. 失权、服务过期或型号不支持的设备不应计入可重发数量；
6. 页面区分失败总数和当前可重发数。

### 17.7 高危操作确认信息不足

**问题**：

RESET / POWEROFF 使用普通确认或 Save 文案，无法体现业务中断风险，也无法让用户核对实际影响设备。

**修改要求**：

1. 标题使用“确认远程重启”“确认远程关机”；
2. 主按钮使用“确认关机 36 台设备”等结果型文案；
3. 展示设备或批次标识、目标总数、告警设备数、当前不可写设备数和状态快照时间；
4. 明确说明可能导致设备离线或服务中断；
5. 明确说明开始下发后可能无法取消；
6. 大批量 POWEROFF 可考虑要求输入影响数量或确认短语。

### 17.8 解绑确认未展示真实级联影响

**问题**：

企业一级解绑可能同时使二、三级账号失权，并清除分组、围栏关系及未写出任务；用户可能误以为只是从当前列表移除设备。

**修改要求**：

提交前由服务端返回实时影响预览：

```text
将移除：
- 2 个二级账号的设备授权
- 5 个三级账号的设备授权
- 3 个分组关联
- 2 个围栏关联
- 4 条尚未写出的指令任务
```

按钮根据账号层级区分：

- 个人、企业一级：解绑设备；
- 企业二级、三级：从当前账号移除或取消设备授权；
- 企业一级主按钮可使用“解绑并移除下级授权”。

提交时仍需服务端再次复检，避免预览后关系发生变化。

### 17.9 重发覆盖旧 attempt，用户无法追溯每次尝试

**问题**：

当前卡片只展示最新发送时间、反馈和失败原因。多次重发后，旧失败原因在 APP 中消失，与“记录永久保留、可追溯”的目标不一致。

**修改要求**：

1. 主卡展示最新 attempt；
2. 详情增加可折叠“尝试记录”；
3. 每次 attempt 展示发起时间、发送时间、最终状态、失败原因和反馈；
4. 明确标记“当前展示最新一次尝试”；
5. 旧 attempt 的迟到反馈不能覆盖最新 attempt；
6. 高危 attempt 还应展示绑定会话、取消请求和状态修正轨迹。

### 17.10 页面缺少数据新鲜度说明

**问题**：

用户长时间停留在记录页时，后台状态可能已变化，但页面仍展示旧状态；弱网刷新失败后旧数据也可能被误认为最新数据。

**修改要求**：

1. 页面展示“最后更新于 HH:mm:ss”；
2. APP 从后台回到前台时刷新；
3. 提供手动下拉刷新；
4. 可使用低频退避轮询或状态推送；
5. 刷新失败时保留旧数据，但显示“状态更新失败”；
6. 刷新失败不能把业务状态改成 FAILURE。

### 17.11 空字段统一显示“—”缺少语义

**问题**：

发送中尚无发送时间、已下发但未收到反馈、指令无需反馈、无失败原因和反馈无法关联都可能显示为“—”，用户无法判断是否需要继续等待。

**修改要求**：

根据实际原因展示：

- 尚未发出；
- 等待设备反馈；
- 暂未收到反馈；
- 本指令无需反馈；
- 暂无失败原因；
- 反馈无法关联。

### 17.12 离线设备提交定位频率缺少生效说明

**问题**：

离线或从未连接的设备允许提交定位频率，但页面不额外提示，用户容易把“保存成功”理解为设备已经切换频率。

**修改要求**：

1. 离线提示“设备当前离线，设置将在恢复通信后尝试执行”；
2. 未连接提示“设备尚未建立有效通信，暂时无法确认何时生效”；
3. 保存结果拆分为“设备资料已保存”和“定位频率任务已受理，尚未生效”；
4. 资料成功、频率失败时分项反馈，成功项不得回滚或重复提交；
5. 提供直接进入该设备指令记录的入口。

### 17.13 编辑页返回无提示丢弃修改

**问题**：

用户修改备注、分组或定位频率后，通过顶部返回、系统返回键或手势返回时，当前规则直接丢弃修改且不提示。

**修改要求**：

- 无修改时直接返回；
- 有脏数据时提示“有未保存的修改，是否放弃”；
- 按钮使用“继续编辑 / 放弃修改”；
- 所有返回入口共用同一脏表单判断；
- 已经提交但结果未知的操作不应被当作普通未保存表单丢弃。

### 17.14 用户体验修改验收标准

第三批体验问题关闭时应满足：

1. 用户能够区分受理、下发、设备反馈和设备执行；
2. 用户能够知道任务为何仍在等待；
3. 弱网和 APP 重启不会诱导用户重复下发；
4. 批量结果能够唯一定位本次批次；
5. 批量失败原因有明确分类和下一步建议；
6. 重发范围、解绑影响和高危操作目标对用户透明；
7. 每次重发 attempt 可以追溯；
8. 页面明确展示数据是否为最新；
9. 空字段具有业务语义；
10. 离线配置任务不会被误解为已经生效。
