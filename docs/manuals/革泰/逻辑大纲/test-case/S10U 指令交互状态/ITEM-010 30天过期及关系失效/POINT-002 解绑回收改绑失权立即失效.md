# 用户故事

## [P1] 验证设备解绑使未写出普通任务立即失败出队
- 测试类型
  - 功能
- 前置条件
  1. CR任务ATT-20261015-110-A1处于SENDING且未写出
  2. qa_s10u_admin当前与S10U000001关系有效
- 测试步骤
  1. 解绑S10U000001并触发关系变更事件
  2. 查询记录与队列
- 预期结果
  1. 任务立即进入FAILURE并保存关系失效阶段、原因和failedAt
  2. ATT-20261015-110-A1从队列删除且后续设备上线也不得写出

## [P1] 验证企业回收和设备改绑清理原主体待发任务
- 测试类型
  - 功能
- 前置条件
  1. 原企业账号qa_s10u_admin对S10U000001有SENDING任务A1和A2
  2. 设备即将被企业回收后改绑给账号qa_s10u_new
- 测试步骤
  1. 执行企业回收并完成改绑
  2. 分别查询原账号任务及新账号队列
- 预期结果
  1. 原账号未写出任务均进入FAILURE并记录企业回收或改绑导致的关系失效
  2. 原任务不迁移到qa_s10u_new名下，新账号队列不包含A1或A2

## [P1] 验证账号失权使普通和高危未写出任务均失败
- 测试类型
  - 功能
- 前置条件
  1. qa_s10u_admin有普通UPLOAD任务ATT-20261015-111-A1和高危RESET任务ATT-20261015-112-A1，均为SENDING
  2. 高危任务绑定session-A且两任务均未写出
- 测试步骤
  1. 撤销qa_s10u_admin对S10U000001的控制权限
  2. 查询两条记录与队列
- 预期结果
  1. 两条任务均立即进入FAILURE且失败原因明确为账号失权或权限关系失效
  2. 两条任务均出队，高危任务即使session-A仍在线也不得写出

## [P3][反向] 验证关系失效后新会话和新账号不得执行旧任务
- 测试类型
  - 安全性
- 前置条件
  1. 旧账号qa_s10u_admin的POWEROFF任务绑定session-A后因改绑进入FAILURE
  2. 新账号qa_s10u_new建立session-B并取得控制权限
- 测试步骤
  1. 触发session-B队列处理
  2. 查询旧任务写出日志与新账号任务列表
- 预期结果
  1. session-B不执行、不复活且不重新绑定旧POWEROFF任务
  2. 旧任务保持FAILURE且sentAt为空，新账号需提交新commandId和attemptId才能下发

## [P3][反向] 验证关系失效与写出并发保持单一最终结果
- 测试类型
  - 可靠性
- 前置条件
  1. ATT-20261015-113-A1为SENDING普通任务
  2. 准备并发触发关系失效与TCP写出成功回调
- 测试步骤
  1. 同时投递两类事件并重复投递
  2. 查询最终状态、队列、通知和统计
- 预期结果
  1. 最终状态只能稳定为SENT或FAILURE之一，已可靠写出事实不得被重复事件反复改写
  2. 队列删除、状态统计、通知和业务副作用均只发生一次
